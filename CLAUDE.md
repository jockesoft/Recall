# CLAUDE.md

Onboarding context for AI sessions working in this repository. Everything below was read from the source on 2026-10-01 (commit `f3e3f57`) and kept up to date since (Web Push added 2026-10-28); claims marked **(inference)** were not seen directly. `AGENTS.md` only points here; this file is the single source of truth. Where it and `README.md` disagree, trust this file and the source.

**Recall.nu** is an ASP.NET Core 10 Razor Pages app for tracking TV series and movies: search TheTVDB, build a library, mark episodes and movies watched, like and rate (1–10), get in-app and push notifications for newly aired episodes, import an IMDb list export, and see TheTVDB and IMDb (via OMDb) ratings side by side. Sign-in is passwordless only: an emailed magic link, or the one-time code in the same email.

## Working agreement

Applies to every session.

- Before starting, check that the working tree is clean and on `main`. If there are uncommitted changes, stop and say so; never stash or discard them.
- Create a branch from the local `main` for each session's work, named with a type prefix and a short kebab-case description: `feat/`, `fix/`, `docs/`, `refactor/`, `test/` or `chore/` (for example `feat/web-push-notifications`). Don't fetch, pull or rebase; the owner keeps `main` up to date.
- Commit to that branch as you go, in logical commits that each build and pass `dotnet test Recall.sln`, with conventional commit messages (for example `feat(push): add push_subscription table and migration`). Keep unrelated changes in separate commits; put CLAUDE.md and README updates in the commit they belong to, or in a final docs commit.
- Never push, publish or set an upstream for the branch, never merge into `main`, never force anything, and never amend or rewrite commits that existed before the session. Don't change git configuration.
- Don't change Docker or compose files unless asked; the owner maintains them. (The current port setup, bound to loopback, is described in section 12.)
- End each session with the branch name and the list of commits (hash and message), and leave the working tree clean.

## 3. Hosting and startup (`Recall.Web/Program.cs`)

**Registration order**

1. `AppCulture.PinToEnglish()` before anything else. Then, when the only argument is `generate-vapid-keys`, the process prints a new VAPID key pair as `Push__PublicKey=…` / `Push__PrivateKey=…` and exits (a one-off helper, see "Enabling push notifications" in the README). When the only argument is `healthcheck`, it runs the container's healthcheck instead (`Infrastructure/Hosting/HealthProbe.cs`): GET `http://127.0.0.1:<port>/health/live` with a 3 s timeout, exit code 0 for a 2xx answer and 1 otherwise, one line of output; the port is the one Kestrel uses (`ASPNETCORE_URLS` before `ASPNETCORE_HTTP_PORTS`, as Kestrel decides; 8080 when neither is set). It runs before the host is built, so it starts nothing. Then Serilog from configuration (`UseSerilog`, console + rolling daily file; levels in section 10, "Logging").
2. `AddRazorPages`, `AddAntiforgery`, `AddHttpContextAccessor`. There are no MVC controllers and no session state.
3. `AddTrustedForwardedHeaders`: X-Forwarded-For/Proto/Host, applied only when the request comes from a trusted proxy. The `TrustedProxies` section (`Infrastructure/Hosting/TrustedProxyOptions.cs`) lists `Addresses` and `Networks`; with both empty the default is loopback plus the private ranges. An invalid entry fails startup.
4. `AddCookieAuthentication`, `AddAuthorization` (no fallback policy).
5. `AddRedisCache`, `AddPostgres` — both throw at startup if their connection string is missing.
6. TheTVDB (`AddTheTvDb`: `TheTvDbClientState` singleton, typed client with a retry pipeline), `AddOmdb`, `AddApplicationServices`, `AddWeeklyDigest(configuration)`, `AddNotifications`, `AddPush(configuration)`, `AddMail`, `AddWatchlistImport`.
7. Health checks, `AddPasswordlessAuth`, `AddRateLimiting`, `IAppUserRepository`, `AddScheduledJobs(configuration)` (Quartz, plus the retention job's options and repository).

All of these live in `Extensions/ServiceCollectionExtensions.cs` (application services) and `Extensions/InfrastructureServiceCollectionExtensions.cs` (Redis, Postgres, cookies, session, rate limiting, Quartz). Add new integrations there, not inline in `Program.cs`.

**Lifetimes**

| Lifetime | Services |
|---|---|
| Singleton | `TheTvDbClientState`, `IDistributedCacheJson`, `IOmdbRequestBudget`, `ILoginAbuseGuard`, `TimeProvider` (`TimeProvider.System`) |
| Scoped | `AppDbContext`, all repositories, all services, snapshot stores, `ICurrentUserService`, `RecallCookieEvents` |
| Transient (typed `HttpClient`) | `ITheTvDbApiClient`, `IOmdbApiClient`, `ITurnstileVerifier`, `IPushSender` (10 s timeout, no redirects) |
| Factory | `IDbContextFactory<AppDbContext>`, for code that fans out in parallel |

**Options binding**: `Configure<T>(GetSection(T.SectionName))` for `TheTvDbOptions` (`TheTvDb`), `OmdbOptions` (`Omdb`), `MailOptions` (`Mail`), `LoginTokenOptions` (`Login`), `TurnstileOptions` (`Turnstile`). No options validation, except `TrustedProxyOptions` (`TrustedProxies`), which is read and validated eagerly at registration. `RetentionOptions` (`Retention`) is bound the usual way. `AddWeeklyDigest` binds `DigestOptions` (`Digest`) and `SiteOptions` (`Site`) and also reads them eagerly: with `Digest:Enabled` true and `Site:BaseUrl` not an absolute http(s) address, or with `Digest:HourUtc` outside 0–23, startup fails with a message that says what to set. `AddPush` binds `PushOptions` (`Push`) and reads it eagerly the same way: with `Push:Enabled` true, startup fails unless `PublicKey` and `PrivateKey` are a P-256 pair in base64url that belong together (checked by signing with one and verifying with the other, `VapidKeys.Problem`) and `Subject` is a `mailto:` address.

**Before serving**: in Production, the Data Protection key folder is checked first (`Infrastructure/Hosting/DataProtectionKeyFolder.cs`): the framework's default folder (`FileSystemXmlRepository.DefaultKeyStorageDirectory`, `$HOME/.aspnet/DataProtection-Keys`; nothing configures Data Protection, and nothing should move the keys or set an application name, which would make existing cookies and unsubscribe links unreadable) must exist and accept a file. It logs the number of key files at Information; otherwise it logs a Critical line naming the folder and the expected owner (UID 65532) and the app exits with code 1, so the deploy's `up --wait` fails instead of the app running on keys it cannot keep. Then `await app.MigrateDatabaseAsync()` (`DatabaseStartup.MigrateAsync`, `Infrastructure/Persistence/DatabaseMigrationExtensions.cs`) applies pending migrations with 10 retries, 3 s apart. Disable with `Database:MigrateOnStartup=false`. In Production it first asks for the applied migrations: a database with none (`__EFMigrationsHistory` missing or empty) gets a Critical line ("has no applied migrations … Not starting") and the app exits with code 1, without creating anything, because on the server that means the compose file points at a new, empty volume, not a new install. `Database:AllowEmptyDatabase=true` lets a genuine first install through (a Warning, then the schema is created); it is not set otherwise. Development and tests are not guarded.

**Middleware pipeline**: developer exception page (Development) or exception handler that logs and redirects to `/Error` + HSTS → `UseForwardedHeaders` → `UseHttpsRedirection` → `UseStatusCodePagesWithReExecute("/Status/{0}")` → `UseStaticFiles` (with `AppShellFiles.PrepareResponse`, the no-cache header for `sw.js` and the manifest) → `UseRouting` → `UseAuthentication` → `DevAuthMiddleware` (Debug builds only) → `UseRateLimiter` → `UseAuthorization` → endpoints. The rate limiter sits after authentication because the `public-details` policy exempts signed-in users. A response that ends with an error status and no body (unknown URL, `NotFound()` from a page, a rejected antiforgery token, a 429) is re-run as `Pages/Status`, which renders inside the layout and keeps the status code; the re-run keeps the original method, so that page has no handlers and ignores antiforgery.

**Endpoints**: `/health` (runs `DbHealthCheck`, a `SELECT 1`), `/health/live` (no checks; what the container healthcheck asks, so a database outage never marks the app unhealthy), `MapStaticAssets`, `MapRazorPages`.

On a phone a caught-up toast with actions puts them under its sentence. How long a toast stays is under "Toasts" below.

### Toasts

Every toast in the app is drawn in one place, the `_ToastMessages` partial in the layout, from the TempData the toast helpers write; no page renders its own and no script writes one. Each toast is the `_Toast` partial (`ToastView`). `ToastMessagesModel.From(TempData)` (`Pages/Shared/`) decides what the partial shows, and `js/tvdb-toasts.js`, loaded by the layout, is the one script. A toast made any other way must go through both. The one toast the browser shows by itself, Share's "Link copied." (`ToastMessagesModel.LinkCopied`, an info toast), is drawn by `_Toast` on the server inside a `<template data-toast-template="link-copied">` (in `_TitleActions`), and `RecallToasts.show('link-copied')` in `tvdb-toasts.js` moves a copy into the stack and starts its countdown: the same markup, timing and pausing as any other.

- **Reading TempData: never `as string` or a cast.** TempData crosses the redirect in a cookie, and the cookie serializer does not give back what was written: a string shaped like a GUID comes back as a `Guid`, one shaped like an ISO date as a `DateTime`, an `int` or a `bool` stays one (a `long` cannot be written at all). Within the request that wrote it, the value is still exactly what was written. So every read goes through `TempDataValueExtensions` (`Extensions/`): `GetText`, `GetInt32`, `GetInt64`, `GetGuid`, which take the value in either shape. The helpers write strings in invariant form (ids, ticks, `Guid` as "D"). From 2026-11-13 to 2026-11-22 the Undo of every mark was missing in real use because the batch id was read `as string`, while every test used a plain dictionary that never serialized. A new TempData key needs a scenario in `ToastTempDataRoundTripTests`, which carries every toast through the real cookie (`TestSupport/CookieTempData`) and fails if a key in `PageModelToastExtensions` has none.

- **How long each stays** is decided in one place, `ToastDurations.For(kind, hasAction)` (`Infrastructure/Display/ToastDurations.cs`): a success or info toast closes itself after 5 seconds; one with an action (Undo, "Rate it", any later button: `ToastView.HasAction`, which a new action must be added to) after 10; an error or a warning never. Nothing "stays until dismissed" because it has an action any more. `SetWarningToast` exists for the rule's sake; nothing calls it yet.
- **On the element**: the duration is `data-toast-duration` in milliseconds, absent on a toast that does not close itself; `data-toast-actions` is there when it has an action, `data-toast-kind` on a caught-up toast. The partial writes the three by hand (`DataAttributes`), because Razor renders a `data-*` attribute with a null value as `data-x=""` instead of leaving it out, and the script and the stylesheet go by presence. (Until 2026-10-06 the old `data-toast-persist` was on every toast for that reason, and no toast ever closed itself.)
- **Countdown bar** (`.tvdb-toast-timer`, `aria-hidden`): a 3px bar along the bottom edge in the toast's accent (`--tvdb-toast-accent`, also its left edge), shrinking to nothing over the duration. Its CSS animation *is* the timer: the script only sets `--tvdb-toast-duration` and `data-toast-running`, and closes the toast (Bootstrap's alert close, so the fade is the same as the close button's) on the bar's `animationend`. A toast that does not close itself has no bar. Without script nothing runs and toasts stay.
- **Pausing** is `animation-play-state: paused` in the stylesheet: while the toast is hovered, while keyboard focus is inside it, and while the stack has `data-toast-paused`, which the script sets when the tab is hidden (`visibilitychange`). It resumes from where it stopped. With `prefers-reduced-motion` the bar is invisible (`opacity: 0`, not `display: none`, which would stop the animation) and still keeps the time.
- **Keyboard and screen readers**: Escape closes the toast that has focus, else the newest (the last in the stack); a modal or an open menu gets its Escape first. The close button stays. A toast never takes focus when it appears and keeps `role="alert"`.
- **Several toasts** each have their own bar and close independently; when one leaves, the others slide to their new place (a short FLIP animation in the script, skipped with reduced motion).
- **Screenshots**: Playwright's `Animations = Disabled` runs finite animations to their end, which would close every toast, so the capture stops the bars where they are first (`FreezeToastCountdownsAsync`).

### Design system

The look is one theme: a dark navy canvas ("ink") with the content on a cream panel ("paper"). `ui-review/UI-INVENTORY.md` (not tracked) describes the UI before this system existed.

**Stylesheets**, loaded in this order by `_Layout.cshtml`: `bootstrap.min.css`, the two Phosphor stylesheets, then `css/tokens.css` → `base.css` → `components.css` → `pages.css`.

| File | Holds |
|---|---|
| `tokens.css` | Every custom property: colours, type scale, spacing, radii, shadows, widths, and Bootstrap's root `--bs-*` variables |
| `base.css` | `@font-face`, element defaults, the two surfaces, focus ring, skip link, icon helpers, type helpers, navbar, panel, footer |
| `components.css` | Bootstrap components themed through their `--bs-*` variables, then the shared components (the partials and repeated patterns) |
| `pages.css` | Pieces that belong to one page or one group of pages |

There is no `!important` in the theme and none should be added. Bootstrap is themed through its own variables: root `--bs-*` values in `tokens.css`, per-component variables on the component class (`.btn-primary { --bs-btn-bg: … }`). Plain rules are used only where Bootstrap has no variable (for example `.form-control:focus`). There are no page-level `<style>` blocks.

**Surfaces.** `:root` carries the values for the dark canvas. `.tvdb-shell`, `.modal-content`, `.dropdown-menu` and `.tvdb-surface-paper` re-point the same `--bs-*` variables (text, muted text, links, borders, danger) and the focus ring at the paper palette, so Bootstrap utilities such as `.text-muted` and `.text-danger` are right on both and nothing inside needs to know where it is.

Seven sizes, used through the tokens, never as literals (an eighth, `text-4xl` at 56px, exists for the landing page's headline and nothing else):

| Token | Size | Use |
|---|---|---|
| `text-xs` | 12px | Fine print, badges, eyebrows |
| `text-sm` | 14px | Secondary text, buttons, labels |
| `text-md` | 16px | Body |
| `text-lg` | 18px | Lead text, `h3` |
| `text-xl` | 24px | `h2` |
| `text-2xl` | 32px | Stat numbers; `h1` on phones |
| `text-3xl` | 40px | `h1` on desktop (`h1` is `clamp(2xl, 5vw, 3xl)`) |

Helpers: `.tvdb-eyebrow` (small uppercase label), `.tvdb-prose` (running text), `.tvdb-meta` (secondary line: dates, runtimes, hints), `.tvdb-mono` (data). Line heights `leading-tight` 1.1, `leading-snug` 1.3, `leading-body` 1.55.

**Spacing and radius.** `space-1` … `space-7` are 4, 8, 12, 16, 24, 32 and 48px. `radius-sm` 4px (chips, code), `radius-md` 8px (buttons, inputs, posters, tiles), `radius-lg` 12px (the panel, cards, modals), `radius-pill`, `radius-round`.

**Icons** are Phosphor, regular and fill weights, and every icon is a constant in `Infrastructure/Display/Icons.cs` holding the full class (`Icons.Series` is `"ph ph-television-simple"`, `Icons.Liked` is `"ph-fill ph-heart"`). Markup writes `<i class="@Icons.Series" aria-hidden="true"></i>`; C# that picks an icon returns the constant. Do not write `ph-…` literals in pages, use Unicode characters or inline SVG as icons, or use Bootstrap's built-in icons (`btn-close`, `navbar-toggler-icon`; the close button is `.tvdb-close` with `Icons.Close`). A new icon is a new constant; `IconsTests` fails if a constant names an icon Phosphor does not have. Icons are decorative (`aria-hidden`); the text or the control's `aria-label` carries the meaning. **A control with visible text is named by that text**: give it no `aria-label`, or one that starts with the visible text (WCAG 2.5.3, label in name; axe's `label-content-name-mismatch`). State goes in `aria-pressed`, a hint in `title`: the full-size watched toggle is "Watched Fri, Sep 11", pressed, described "Mark as unwatched". Only a control with no text (the episode list's watch dots) needs an `aria-label`. Size helpers: `.tvdb-icon--sm|md|lg|xl`, and `.tvdb-icon--fw` for a fixed-width box in menus and lists. The one icon drawn from CSS is the external-link arrow after `.tvdb-metalink[target=_blank]`.

**Page frame.** Every page puts its content in one `<div class="tvdb-shell">`. Two widths only: the full panel (1100px) for grids and detail pages, and `tvdb-shell--narrow` (680px of content) for forms and text pages; do not narrow content with grid columns. Every page has exactly one `h1` and heading levels do not skip (`h2` sections, `h3` inside them). A way back is `<a class="tvdb-back-link">` with `Icons.Back`, always the first thing inside the panel, except on a page with a title hero (Series Details), where it is the first thing in the hero. The layout provides the skip link (`#main`), marks the current navigation item with `aria-current="page"` (`CurrentIf(...)` in `_Layout.cshtml`), and the mobile menu is `#mainNav`.

**States.** "Nothing here" is the `_EmptyState` partial (`EmptyStateModel`: icon, heading, sentence, an optional button and an optional quieter second one, heading level; `Inline = true` inside a section, including an empty section of a page that has other content). It is also the body of the status, error, sign-in-link and not-found pages, with `HeadingLevel = 1`. Do not use an alert or a line of muted text for an empty page. A detail page that cannot load its title renders the same partial itself and sets the status code: 503 when TheTVDB failed, 500 for anything else, and (Episode Details) 404 for an episode that does not exist, with a link back to the series the visitor came from. `NotFound()` from a page model still goes to `Pages/Status`.

**Links.** A link in running text keeps its underline (Bootstrap's default). A link that stands on its own in a list or a card (an episode title, a person's name, a card title) is `.tvdb-link-plain`: no underline until hover or focus. `.tvdb-metalink` is the quiet underlined link inside a value or a source line.

**Actions.** A page has one amber `btn-primary`: the next thing to do ("Mark S05E07 watched", "Add to library", "Mark as watched"). A toggle that is on is `btn-watch--on` ("Watched Fri, Sep 11", Episode Details); a state that is not a button is, in the action row of `_TitleActions`, the quiet `.tvdb-status-box` ("Up to date", "Watched Fri, Sep 11"). Secondary actions are `btn-outline-dark`. Removing something is never a button of its own in the action row: on Series and Movie Details it is an entry of the action row's "⋯" menu that opens the `_ConfirmModal` partial (`ConfirmModalModel`), whose confirm button is a `btn-danger`. The only other `btn-danger` is the final button of "Delete my account". "Stop watching" on Series Details is in the same "⋯" menu, but it posts at once with no dialog: nothing is lost and the toast has an Undo. A quiet action that destroys the account itself is `.tvdb-quiet-action--danger`. Do not use the browser's `confirm()`. Rarely used actions on a list go in a `.tvdb-icon-button` (`Icons.More`) dropdown. Interactive targets are at least 36px. Button sizes go by role: a page's actions (primary and secondary) are the default size; an action that belongs to a section or to one row of a list ("Mark all as read", "Mark read", "View import", "Show all N", the filter pills) is `btn-sm`; the landing page's "Get started" is the one `btn-lg`.

**Rhythm.** Sections of a page (an `h2` and what belongs to it) are `space-6` apart: wrap them in `.tvdb-page-section`, or on a text page put `.tvdb-text-page` on the panel. An `h2` sits `space-3` above its content (set on `h2` itself; do not add `mb-*` to one). An `h1` is `mb-4` above the page, or `mb-2` above a lead sentence that then carries the `mb-4`. The Details pages' ruled `.tvdb-section` and the landing page keep their own, larger steps.

**Titles in lists and on cards** have two styles and no others, defined once in `components.css`: a row's title (episode, search result, import row, notification) is the UI face, semibold, body size; a card's title (poster card, upcoming card, liked episode, person) is the same a step smaller. A read notification is the one exception: regular weight, because bold is its unread signal. A new list or card adds its title class to one of those two rules.

The "⋯" menu holds "Stop watching" (`#stopWatching`, when `DetailsModel.CanStopWatching`; see "Stopped watching" in section 5) and "Remove from library…" (`#removeFromLibrary`, opening the `removeFromLibraryModal` confirmation with the old wording). **Movie Details** (redesigned 2026-11-23) has Series Details' structure and reuses its partials and classes: `_TitleHero`, `_TitleActions`, `.tvdb-section-links`, `.tvdb-fact-list`, the compact cast column. Built by the Movie page model's `BuildHero`:

The source line closes the panel.

Elsewhere (Episode Details) the cast is portrait cards: exactly one full row on wider screens, a sideways-scrolling row on phones sized so the next card peeks in. Every detail page ends with a `.tvdb-source-line` (TheTVDB id, IMDb id); ids are not shown anywhere else.

**An episode's image** is decided in one place, `EpisodeArt.Resolve` (`Services/EpisodeArt.cs`), for Episode Details, the Dashboard's continue-watching cards and the Favorites episode cards, so the same episode never shows a still on one page and an empty frame on another. In order: the episode's still in the series aggregate; the still on the episode's own cached record (it can have one before the aggregate is next refreshed); the series' background art (`SeriesAggregate.BackgroundUrl`, 16:9 like a still); nothing, and the page draws its placeholder ("No image yet"). `ITheTvDbService.GetEpisodeArtAsync` applies it and reads the episode's record only when the aggregate has no still. TheTVDB has no still at all for many episodes (a third of the older ones in the dev data; some series have almost none), so the background art is the normal picture for those, not a stopgap. Background art standing in for a still gets `alt=""` and is left out of the episode's structured data (`EpisodeArt.StillUrl`). A new place that shows an episode's picture uses the same call. Upcoming cards and notifications show the series poster by design; OMDb is never a source of images.

**Dashboard.** Three small linked stats in one row at every width (`.tvdb-stat-row` of `.tvdb-stat-item`; the same compact style, without links, is Admin's). The first section is "Continue watching" (the `_CatchUpCard` partial and `CatchUpItem` keep their older names): the active series in the order of `ContinueWatchingOrder`, and under them one quiet link, "N series you haven't watched in a while", to the Library's dormant group (no link when N is 0; those series get no card). The "Unwatched episodes" stat still counts every series. A card's image follows the rule every page shares (see "An episode's image" below): the episode's still, else the series' background art, else a dark placeholder; never the poster, which is the wrong shape. Each card has a "⋯" menu in its top right corner (the round `.tvdb-watch-badge--menu` button, a Bootstrap dropdown labelled "More actions for {series}", positioned `fixed` so the frame's clipping does not cut it) holding "Stop watching": the card goes and the toast offers Undo. The one-tap mark button stays bottom right. A stopped series is in nothing on this page except the "Tracked series" count. The caption's shade sits only behind the text and stops short of black. Upcoming cards are compact, in two columns from 768px, in the order poster, series and episode, then the date with a small countdown as a secondary line (right-aligned on wide cards; on phones the last line of one text column); under a "Today" or "Tomorrow" heading the card shows neither, only the time when one is known (`UpcomingEpisodeCardModel.ShowDate`). Upcoming lists the episodes not yet released (see "Released" in section 5) whose air date is within 30 days, soonest moment first; the groups (Today, Tomorrow, This week) and the "This week" stat go by `ReleaseMoment.GroupDate`, the UTC date of the moment when the time is known (Gold Rush at 20:00 ET on Oct 2 is under "Tomorrow" on Oct 2 UTC), else the air date.

**Poster cards** (`_SeriesCard`, `SeriesCardModel`): no type badge on the poster. The meta line under the title says "Series · 2008" or "Movie · 1995", or "Movie · watched Sep 25" when the card passes a `Caption`; a series under Watching also gets `ProgressText` ("6 of 16 · S05", from `SeriesWatchProgress.CurrentSeason`), with the bar on the poster as the glance. **Landing.** A hero (`.tvdb-landing-hero`: headline at `text-4xl`, one sentence that names series and movies, one "Get started" button; the navbar has the only other way in), a product preview, three features with icons, and "How it works" (`.tvdb-steps`, also used on Import). The preview (`.tvdb-landing-preview`) is the app's own component classes as static markup: no links or buttons, `aria-hidden`, `pointer-events: none`. Its artwork is abstract (`.tvdb-art` with the `--tvdb-art-*` tokens): TheTVDB's images are licensed for display with its metadata, not for marketing, so never put a real poster or still on the landing page.

**Forms.** The field comes first; explanation that is not needed to fill it in goes below the form (the sign-in page's benefits list). A field has one message area (`.tvdb-field-message`): a server-side message and a live status line never show together, and the hint is a line of its own under it (Edit profile). Buttons sit in `.tvdb-form-actions`: one row, Cancel first, the saving action last, on the right. Validation messages are written for people ("Enter a valid email address."), set with `ErrorMessage` on the attribute. After a sign-in link is requested the page shows a state of its own: envelope icon, "Check your inbox", the address, the link's real lifetime (`LoginTokenOptions.TokenLifetimeMinutes`), the code form (`.tvdb-code-form`: a field with `inputmode="numeric"` and `autocomplete="one-time-code"` beside the page's one `btn-primary`, "Sign in"; one message area, `LoginModel.WrongCodeMessage` or, locked out, `TooManyCodesMessage` in place of the field) and "Use a different email" ("Request a new email" when locked out).

**Cookies.** There is no cookie notice and no consent prompt: everything the app stores in a browser is strictly necessary, and the Privacy page is the one place that explains it. What is stored: the sign-in cookie (`Recall.Auth`, 30 days sliding, set at sign-in), the antiforgery cookie (session; set on pages that render a form, which for a visitor is the sign-in page and the three Details pages, not the landing or Privacy page), and the TempData cookie (only between a POST and the page that shows its toast). Nothing is kept in local or session storage (the layout still removes the old `recall.cookie-notice-dismissed` key from browsers that have it; that line can go after a while). A browser where the user turns push notifications on also keeps the service worker registration and its push subscription; the Privacy page says so while push is enabled. Third-party requests: posters and stills from `artworks.thetvdb.com`, and Cloudflare Turnstile on the sign-in page when its keys are set. Emails load nothing from anywhere (no images, no tracking). Anything new that is stored in a browser, or loaded from another host, needs a line on the Privacy page, and anything that is not strictly necessary would need a consent prompt first.

**Avatar.** There are no profile pictures. The signed-in user's avatar is the `_Avatar` partial (`AvatarModel(name, size)`): initials from `Initials.Of(name)` on amber, in three sizes (`sm` navbar, `md` phone menu, `lg` profile). It is `aria-hidden`; the name beside it or the control's `aria-label` carries the meaning. Where the avatar is a control's only visible content (the navbar's account menu), that label must still start with the initials, because WCAG 2.5.3 (label in name) is about what is visible, not what is exposed: `AvatarModel.AccountMenuLabel` gives "DU, account menu" ("Account menu" when there are no initials). Cast and crew without a photo use the same `Initials.Of`.

**Status words.** A stored status is never printed as its enum name. `ImportStatusDisplay.For(status)` is the one mapping for import rows (label, badge colour, icon): Imported is ok, Already had it and Unsupported neutral, No match amber, Failed danger, Waiting neutral. A new status enum shown to people gets a mapping like it, and a test that every value has one.

**Lists of results** (Search, Import, Notifications) are lists, not tables: a row is a title, a muted meta line ("Movie · 1995", "Movie · rated 8"), an optional badge, and detail text beneath, so nothing scrolls sideways at any width. Search shows the first 20 results and reveals the rest (already on the page, `hidden`) 20 at a time with "Show more". A result's title is an `h2` in the UI face at body size, like every other list title, not the display face; overview lines are capped at 70ch. The search field is wide and its button keeps its natural width beside it at every width. An overview is English when TheTVDB has one; otherwise the original, marked with its `lang` (`SearchResultItem.OverviewLanguage`, from `SearchResultMappings.ToLanguageTag`). Results the user already has carry an "In library" or "Watched" badge (`SearchModel.LibraryBadge`); a series they stopped watching says "Stopped" instead, as a neutral badge with `Icons.Stopped` (`SearchModel.IsStopped`).

**Profile** is full panel width: a header (avatar, name and email once, and the watch-time figure: `WatchTimeSummary.Readable`, e.g. "1 month, 3 days", "across 815 episodes and 3 movies", as a link to Stats; it is the Stats page's own total, from `IStatsService`), then `h2` sections: Favorites (one `.tvdb-poster-row` of posters and a "See all" link in a `.tvdb-section-head`), Import (one sentence, `ProfileModel.ImportSummary`), Notifications (only while push is enabled; `#push`), Account (facts, with "Sign out" and "Delete my account" as quiet actions at the bottom). The Notifications section has two `.tvdb-setting` rows like the weekly email's ("This device" and "Quiet hours") and an `h3` "Your devices" list (`.tvdb-device`: `Icons.Device`, label, "time zone · added date", a `btn-sm` Remove). What "This device" shows is decided in the browser by `tvdb-push.js`, which reveals one `data-push-state` block: `off` ("Turn on"), `on` ("Turn off"), `ios` (Add to Home Screen steps, with `Icons.Share`, for Safari on an iPhone or iPad not opened from the Home Screen), `unsupported`, `denied` (how to unblock it). The script compares a SHA-256 of the browser's own subscription endpoint with the rows' `data-endpoint-hash` to mark "This device"; the page never contains an endpoint.

**Notifications.** A row is the series poster thumbnail, the title, the text, and a foot line with the age and "Open episode". The row itself is the button that opens the episode (a POST, since it marks the notification read); beside it an unread row has a small "Mark read" button (`OnPostMarkReadAsync`). Unread is shown one way only: a dot and a bold title.

**Stats** (`Pages/Account/Stats`) is full panel width: a sentence that adds the total in days ("That's about 34 days of watching."; left out below two days, where the tile's hours say it all), four totals (`.tvdb-stat-row--four`, two by two on a phone), then `h2` sections: Month by month, then Most watched series, Genres and Your ratings in `.tvdb-stats-columns`: one column, and from 992px two, so series and genres sit side by side with the ratings under the series at one column's width. In a ranked row the figures are on their own line under the label on a phone, and beside it from 576px. Charts are drawn by the server as lists, with no script and no chart library: twelve columns (`.tvdb-month-chart`) and ranked rows with a bar (`.tvdb-bar-list`). A bar's length is `--tvdb-bar`, a percentage set inline on the element; that is data, not a design value, and the one inline style the theme allows. Every chart says its figures in text: a month column carries a visually hidden sentence ("October 2026: 12 episodes, 1 movie, 9 h 40 min"), a ranked row shows its name and value, and the bars themselves are `aria-hidden`; the monthly figures are also a table behind a native `<details>`. On a phone a month's label is one letter. Amounts are written by `StatsFormat` ("9 h 40 min", "312 h"), months by `DisplayDate.Month` / `MonthShort`. States: a user with nothing gets the page-level `_EmptyState`; one whose history is all bulk-marked or imported gets totals and top lists with an inline `_EmptyState` where the chart would be; no ratings is an inline `_EmptyState`; the Genres section is left out when no title has genres.

**A page that waits for a background job** (Import while it is matching) shows a progress bar with the count in words ("12 of 40 rows matched") and reloads itself with a `setTimeout` every `RefreshSeconds`; do not use `<meta http-equiv="refresh">`, which axe reports.

**Dates** are formatted only by `Infrastructure/Display/DisplayDate.cs`: `DisplayDate.Format(date, today)` gives "Sat, Sep 4" for a date in the current year and "Sep 4, 2026" otherwise; it also takes the date strings TheTVDB sends. `DisplayDate.Short` is the same without the weekday ("Sep 4"), for a tight spot such as a poster card's meta line. `today` is the page model's `Today` (from `TimeProvider`). `DisplayDate.Time` gives a time of day ("8:00 PM"). `DisplayDate.Month` and `MonthShort` give a calendar month ("October 2026", "Oct") for the Stats chart. `DisplayDate.Relative` ("3h ago") is for notifications only. Machine-readable output (sitemap, JSON-LD) keeps ISO dates and does not use it.

**Release times** (when an episode airs) are written by the `_ReleaseTime` partial (`ReleaseTimeModel`), on the Upcoming cards and on Episode Details: a `<time>` element whose `datetime` is the release moment in UTC (`ReleaseMoment.DateTimeAttribute`, "2026-10-03T00:00:00Z") and whose text is what the server can say, TheTVDB's air date and the series' own time and zone (`ReleaseText`: "Fri, Oct 2 · 8:00 PM ET"). `js/tvdb-local-time.js` rewrites every `time[data-local-release]` into the viewer's own date and time with `Intl.DateTimeFormat('en-US')`, in `DisplayDate`'s style ("Sat, Oct 3 · 2:00 AM"; `data-local-release="time"` gives the time alone, under Today or Tomorrow), and keeps the server text as the element's `title`. Nothing is stored and nothing is sent back. A fallback moment (no air time known) is written with its date only (`datetime="2026-10-02"`, no `data-local-release`), is never given a time and is not rewritten. Series Details uses it for an episode not released yet (its row in the season card, and the up-to-date box's next release); released episodes there, and the digest, show dates only, by `DisplayDate`.

**Logo.** `wwwroot/images/logo.svg` (navbar lockup, cream wordmark), `logo-light.svg` (ink wordmark), `logo-mark.svg`, plus `favicon.svg`, `favicon.ico`, `apple-touch-icon.png` and `images/og-image.png`. All are generated by `ui-review/logo/render.sh [bookmark|play|check]` from `make_logo.py`, which draws the mark and converts the wordmark to paths; edit the script, not the files. The navbar logo is sized by height (32px, 28px on phones). The mark is the bookmark variant (the script's default). The scripts need the Python packages in `ui-review/logo/requirements.txt`.

## 5. Domain model

All user data hangs off `AppUserEntity` (Guid PK, equal to the `NameIdentifier` claim), with cascade delete.

**User-owned tables.** These hold rows that belong to one user: `tracked_series`, `tracked_movie`, `episode_watch`, `user_movie_watch`, `user_like`, `user_rating`, `notification`, `notified_episode`, `login_token`, `digest_send`, `push_subscription`, `watchlist_import_job` and (through its job) `watchlist_import_item`, plus the rows of `email` addressed to the user. The digest preference, the dismissed offer and the quiet-hours setting are columns of `app_user` and go with the row. The `Cached*` tables are shared metadata and belong to nobody.

**Deleting an account.** `Pages/Account/Delete` ("Delete my account", reached from the bottom of Profile's Account section) explains what goes and that it cannot be undone, and enables its final button once the username (or email address) is typed; the POST checks that again. `IAppUserRepository.DeleteAccountAsync` then deletes every user-owned table above and the user row in one serializable transaction, and refuses (`AccountDeletionResult.OnlyAdmin`) when the user is the only admin; the page shows an explanation instead of the form in that case. Afterwards the handler signs the browser out, sets a success toast and redirects to the landing page. Other sessions of the account stop at their next cookie revalidation (at most 5 minutes, `RecallCookieEvents`), since the user row is gone; until then a write from such a session fails on the foreign key. Recall ratings are computed from `user_rating` on each read, so they change at once. Signing in again with the same email creates a new, empty account. Database backups (about 9 days) and server logs keep deleted data until they expire; the Privacy page says so.

**A new user-owned table must be added to `DeleteAccountAsync`** (and to the list above). `AccountDeletionTests` (which seeds `push_subscription` too) in `Recall.Tests.Postgres` asks the database for every table with a `user_id` column and fails if any still has rows of a deleted user, or if the test does not seed it.

**Weekly digest** (`Services/Digest/`). Opt-in: nothing is sent to a user whose `digest_opted_in_utc` is null. It is switched on from Profile's "Weekly email" row or from the Dashboard's one-time offer ("Turn it on" / "No thanks", both POST; the offer shows until either is answered), and off from Profile or the link in any digest. **It is live in production**: `.env.prod` sets `Digest__Enabled=true`, `Digest__MaxPerRun=50` and `Site__BaseUrl`. The default in `appsettings.json` is still off, so a local or test instance sends nothing and hides the switch and the offer unless it sets `Digest:Enabled` itself.

- **Content** (`DigestBuilder`, pure): three sections over the 7 days before and after the run, by release moment (see "Released" below; Gold Rush S17E01, 20:00 ET on Friday Oct 2, is under Coming up in that Friday's 15:00 UTC digest and under New seasons a week later). New seasons (a regular season's first episode released in the past week and is unwatched; any tracked series, dormant ones included), Ready to watch (unwatched regular episodes released in the past week, for series in the main continue-watching list, in that order, minus those already under New seasons), Coming up (regular episodes released in the next week and not already marked, for every tracked series that is not dormant). The dates in the email stay TheTVDB's air dates. Specials are never mentioned; dormancy is `ContinueWatchingOrder.Arrange`'s call. A series the user stopped watching is in none of the three. Ten lines per section, then "and N more". Nothing to say means no email.
- **Email** (`DigestEmailRenderer`): HTML and plain text. No images, no tracking pixel, no redirect links; "Metadata provided by TheTVDB" and the unsubscribe link in both parts. The HTML is table layout with inline styles and its own literal colours and `!important` in a dark-mode block: mail clients need that, and the theme's rules about tokens do not apply inside an email.
- **Links** are absolute, built from `Site:BaseUrl`, since the job has no request.
- **Unsubscribe**: the token (`DigestUnsubscribeTokens`) is the user id protected with ASP.NET Data Protection under its own purpose; it does not expire and depends on the persisted key ring. The link in the body opens `/Digest/Unsubscribe`, a page with a button that POSTs (a GET changes nothing, so mail scanners cannot unsubscribe anyone). The `List-Unsubscribe` header points at `/Digest/OneClick` with `List-Unsubscribe-Post: List-Unsubscribe=One-Click`. Both answer the same whether or not the account exists.
- **Sending** (`WeeklyDigestService`, run hourly by `WeeklyDigestTimer`): `DigestSchedule.DuePeriod` says which week is due (the configured day and UTC hour, for `Digest:CatchUpHours` afterwards). Up to `Digest:MaxPerRun` opted-in users without a ledger row for that week are handled per run. `IDigestRepository.RecordAsync` writes the ledger row and the queued email in one `SaveChanges`, and returns false on the unique index, so nobody gets a week twice. A week with nothing to say is recorded as `Skipped`. A user whose digest fails gets no ledger row and is retried next hour; an email that fails to send is retried by the mail queue and never re-queued.
- **API cost**: none. `DigestComposer` reads series through `ITheTvDbService.GetCachedSeriesAggregateAsync` (Redis, then the Postgres snapshot, never the API) and skips a series that is not cached; one run reads each series once.
- **Preview**: `/Admin/DigestPreview` composes a digest for a date without sending or recording. Outside Development an admin can only preview their own.

**Push notifications** (`Services/Push/`, `Infrastructure/Push/`). Off unless `Push:Enabled`; while off, Profile, Admin and Privacy say nothing about push and nothing is sent.

- **Subscribing** happens on Profile: "Turn on" calls `Notification.requestPermission()` from the button's click handler only (never on page load; a pipeline test and the UI review's push checks hold it to that), registers `/sw.js` with scope `/`, subscribes with the VAPID public key (`data-push-key`) and fills a hidden form (`pushSubscribeForm`) that is posted normally, so antiforgery, the redirect and the toast work as everywhere. `OnPostSubscribeDeviceAsync` checks the input with `PushSubscriptionInput.Check`: the endpoint must be https on the default port at a known push service (`KnownServices`: `fcm.googleapis.com`, `push.apple.com`, `push.services.mozilla.com`, `notify.windows.com` and their subdomains), since the server later POSTs to it, and the keys must decode to 65 and 16 bytes. The label comes from the user agent (`DeviceLabel.FromUserAgent`: "Chrome on Android", "Safari on iPhone"; an iPad's Home Screen app says "Mac"); the time zone is the browser's IANA id, kept only when the server knows it (`DeviceTimeZone.Normalize`, else "UTC"). `IPushSubscriptionRepository.SaveAsync` upserts by endpoint: the same browser again is updated, a browser subscribed for another account moves to this one as a new device. "Turn off" unsubscribes the browser and posts its endpoint; "Remove" on a row deletes any of the user's devices (and unsubscribes the browser too when it is this one).
- **Sending** is done by `NewEpisodeNotificationTimer` through `IPushNotificationService`. Each run first releases due holds (`ReleaseHeldAsync`), then creates notifications as before, then, for each user who got at least one, calls `SendNewEpisodesAsync(userId, runStartedUtc)`: one push per device summarising the user's unread new-episode notifications created since then (`PushSummary.For`: one episode is "Silo: S02E05 is out" and opens `/Episodes/Details/{id}`; more are "3 new episodes: Silo, The Bear and 1 more" and open `/Account/Notifications`). Pushing is after creating and in its own try/catch per user, so a push failure never costs a notification. The run logs "NewEpisodeNotificationTimer: N push(es) sent, H held for quiet hours, F failed (R expired subscription(s) removed, D held push(es) dropped as already read)." at Information.
- **The push itself**: `WebPushSender` (typed client over `Lib.Net.Http.WebPush`): payload JSON with title, body, URL and icon only, encrypted `aes128gcm`, VAPID-signed, TTL 24 hours (`WebPushSender.TimeToLive`), normal urgency (no `Urgency` header, which RFC 8030 reads as normal), and `Topic` = the user id in "N" form, so a push service keeps only the newest undelivered push per user. The service worker shows every push with one tag (`recall-new-episodes`, `renotify`), so a newer one replaces the older in the tray; a subscription belongs to one user, so that is a tag per user. A tap focuses an open Recall window and navigates it, or opens one, and only ever to a same-origin URL. A tap does not mark the in-app notification read (that is a POST).
- **What an answer does**: 201 marks `last_success_utc` and clears any hold; 404 or 410 deletes the subscription (`PushDelivery.Gone`); anything else, a timeout or no connection is `Failed` and keeps it. `IPushSender` never throws for a failed delivery.
- **Quiet hours** (`QuietHours`, pure): 22:00–08:00 on the device's clock, per user (`app_user.push_quiet_hours`, on by default; Profile switch). A push due then is held on the subscription: `held_since_utc` (the earliest notification time it covers; a second hold keeps the first start) and `held_until_utc` (the next 08:00 in the device's zone, daylight saving included). `ReleaseHeldAsync` takes subscriptions whose time has come, or whose user turned quiet hours off, summarises what is still unread since `held_since_utc`, and sends it; if everything was read the hold is dropped; a failed release clears the hold rather than retrying all day. A daytime push to a device that still holds one covers both. The job runs hourly (simple schedule), so a held push arrives within the hour after 08:00. The admin's test push ignores quiet hours.
- **Retention**: a subscription with no successful push for `Retention:PushSubscriptionDays` (180) days, counted from its creation when none ever succeeded, is deleted by `PruneOldDataTimer`.
- **iPhone**: iOS and iPadOS only offer push to a Home Screen web app, which keeps its own cookies, while the emailed link opens in Safari. Signing in there is done with the code from the same email (see "The sign-in code" in section 8); Profile's iOS steps say so.

**There are no series, season, episode or movie tables.** Metadata exists only as TheTVDB ids on user rows plus JSON snapshots in the cache tables, deserialized into `Domain/TheTvDb` records (`SeriesAggregate`, `Series`, `Episode`, `MovieAggregate`).

**"Watching" vs "watched" is derived, never stored.** `LibraryModel.ClassifyTrackedSeriesAsync` computes it per request, with the section of a series decided by `SeriesLibraryStateRule.Of` (which Stats also uses for "series finished"):

- **Watching**: tracked series with at least one aired regular episode not marked watched, and every series never started (no regular episode watched), ended or not, including one with nothing aired yet.
- **Up to date**: started, no aired regular episode unwatched, and TheTVDB status is not "Ended".
- **To watch**: movies on the watchlist (`tracked_movie`), most recently added first.
- **Watched**: started, no aired regular episode unwatched, and status is "Ended"; watched movies are listed here too.
- **Stopped**: the user stopped watching it, whatever its progress. This one is stored (`stopped_utc`), and it comes before the others.

"Started" is `SeriesWatchProgress.HasStarted`: at least one regular episode watched. Series Details follows it too: with no aired regular episode left, a started series reads "Up to date" and one never started reads "In your library · nothing aired yet". A special does not start a series, and "nothing left to watch" is not "watched it": `IsUpToDate` alone is also true for a series with nothing aired. The Dashboard, the digest and Stats agree with this by construction: the Dashboard and the digest list series by their next episode (so a never-started series with episodes is in "Continue watching" and "Ready to watch", and one with nothing aired is in neither), and Stats counts "series finished" with the same rule.

"Regular" means not a special: see the specials rule below.

**Released: the release moment.** TheTVDB gives an air date with no time zone, plus the series' air time (`SeriesAggregate.AirsTime`, "20:00") and country of origin (`OriginalCountry`, "usa"). `EpisodeRelease.MomentUtc(airDate, airsTime, country)` (`Services/WatchTracking/EpisodeRelease.cs`, pure) turns them into a `ReleaseMoment` in UTC: the air date at the air time in the zone that country's broadcasters schedule by (a table of about 60 countries; one zone for a country with several: the US and Canada Eastern, Australia Sydney, Brazil São Paulo, Russia Moscow, Mexico Mexico City, Indonesia Jakarta), daylight saving included (a time skipped by the spring change is moved an hour on; an ambiguous one takes the later). Gold Rush S17E01, aired 2026-10-02 at 20:00 in the US, is released 2026-10-03 00:00 UTC. When something is missing the moment is late, never early: a known country without an air time is midnight local at the end of the air date; an unknown country is 12:00 UTC the day after the air date (the end of that date everywhere); no air date is no moment. Fallback moments have `IsTimeKnown` false and are never shown as a time. It needs nothing that is not already in the cached aggregate: no extra request and no migration (the zone data is the system's: the hardened runtime image includes the time zone database, checked for all 58 zones of the table).

- **Released** (`WatchableEpisode.IsReleasedBy(now)`, `ReleaseMoment.IsReleasedBy`) decides everything that says an episode exists: progress (released, watched and unwatched counts, the next episode, so the Library sections, Continue watching, Stats' series finished and the caught-up toast's "Next episode … on"), new-episode notifications, the digest's windows, the Dashboard's Upcoming, the Series and Episode Details "Aired"/"Airs" wording and next-air date, and the dormant premiere rule. An episode without an air date is never released, and progress leaves it out as before.
- **May be marked** is generous and by date: `AirDate.MayBeMarked(airDate, now)` is true when the air date is on or before the UTC date fourteen hours from now (the earliest zone, UTC+14), or unknown. Someone who watched an episode in their own evening can always mark it, wherever they are, even before its moment in UTC. Every watch write and the Details pages' buttons use it.
- **Not moved to the moment**: the still recheck schedule (`StillRecheck`) and the sitemap, which go by the air date.
- `AirDate.Now(timeProvider)` gives the current UTC moment; `AirDate.Today(timeProvider)` the UTC date, still used for display and for day-based rules (dormancy).

**Progress** is computed by `Services/WatchTracking/WatchProgressCalculator.Build`: order episodes in *watch order* (`OrderByWatchOrder`: numbered seasons, then the specials, then anything without a season; tie-break by id), keep the regular episodes released by now (see "Released" above), and the next episode to watch is the first of those without an `EpisodeWatch` row. Episodes flagged `IsMovie` are excluded. `CurrentSeason` is the same count within the next episode's season. The episode list always comes from the series aggregate.

**"Continue watching": order and grouping** are decided in one place, `Services/WatchTracking/ContinueWatchingOrder`, for the Dashboard's Continue watching cards and the Library's Watching section (at every width). Nothing else sorts or splits those lists, and the Library's other sections stay alphabetical.

- **Order** (`Order`): series with watch activity come first, most recently watched first; then series with nothing watched yet, most recently added to the library first (`tracked_series.created_utc`); ties by name, then id. Activity is the latest `WatchedUtc` of any of the user's episode watches for the series, specials included: a special never drives the next episode, but watching one counts as watching the series. It comes from `IEpisodeWatchRepository.GetLastWatchedUtcBySeriesAsync(userId)`: one `GROUP BY` query per page load for all of the user's series, with no cache.
- **Grouping** (`Arrange`, which returns the main list and the dormant group, each ordered): a series in the queue is dormant, "haven't watched in a while", when its last activity is more than `Library:DormantAfterDays` days ago (default 90; counted in UTC dates), or, for a series never started, when it was added that long ago. 0 or less turns the feature off. A series with no known date is never dormant, and neither is one with nothing to watch yet (no aired regular episode: an announced series, or one with only specials). The Library passes those to `Arrange` as `nothingToWatch`; they stay in the main list of Watching without a progress line, and an announced series keeps its place in the digest's "Coming up" however long ago it was added.
- **Coming back**: watching anything brings a series back by itself. A dormant series also returns to the main list while the first episode of one of its regular seasons was released within the last `Library:PremiereReturnDays` days (default 14; `HasRecentPremiere`). It is placed after the series with real activity and before those not started yet. An ordinary episode does not bring a series back (an abandoned weekly show airs all the time), and neither does a special.
- **Where it shows**: the Dashboard lists only the main list and links to the rest. In the Library, Watching and its count are the main list; the dormant series are a sub-group inside the Watching section ("Haven't watched in a while N", an `h3` in a `.tvdb-subgroup`): collapsed behind a "Show N" button from 576px, a sideways-scrolling row with "See all N" on phones, and `/Library?section=dormant` on its own.

The settings are `LibraryOptions` (`Library` section), bound with `BindConfiguration` in `AddApplicationServices`.

**Specials (season 0) never count toward progress** (`WatchableEpisode.IsSpecial`). They are in the ordered episode list, shown last on Series Details in a dashed season card labelled "not counted in progress", and can be marked watched there, but `WatchProgressCalculator.Build` leaves them out of everything it derives: they are not in the released, watched or unwatched counts, and a special is never the next episode. So a series whose regular episodes are all watched is up to date (Series Details header, Library section, Dashboard) whatever specials remain, and a special is never a catch-up card. "Earlier" is judged within the same kind (`CountPriorUnwatched`, `IdsThrough`): catching up to S02E03 never marks a special, and marking a special never marks the series. `WatchProgressCalculator.DefaultSeason` picks the season card a series page opens: the next episode's season, else the latest numbered season, and the specials only when the series has no other season. An episode with no season number is not a special. Not covered by this rule: Upcoming on the Dashboard and new-episode notifications still include a special that airs.

**Watch writes go through `IWatchProgressService`**, never straight to `IEpisodeWatchRepository`: `MarkEpisodeWatchedAsync` / `MarkEpisodeWatchedUndoablyAsync` / `ToggleEpisodeWatchedAsync` first verify the episode belongs to the submitted series (the aggregate, falling back to the episode's own record) and reject an episode that may not be marked yet (`AirDate.MayBeMarked`, see "Released" above). `MarkWatchedThroughAsync` marks the target and every earlier episode of the same kind (see the specials rule above), skipping any that may not be marked yet.

**"You're up to date" / "You've finished".** When a mark takes a series from having unwatched aired regular episodes to having none, the marking methods of `IWatchProgressService` return a `SeriesCaughtUp` (null otherwise). `WatchProgressService` decides it by comparing the series before and after the write with `SeriesLibraryStateRule`: before, something aired was unwatched; after, the state is `UpToDate` or `Finished`. So it never fires on an unmark, on marking a special (specials change neither side), on a refused mark, or when the series was already up to date, and it fires in whatever order the episodes were marked. Every way of marking carries it: `MarkEpisodeWatchedAsync` / `ToggleEpisodeWatchedAsync` (which return `EpisodeWatchResult`: the outcome plus this; the episode toggles and the header's next-episode button), `MarkEpisodeWatchedUndoablyAsync` (the Dashboard's one-tap mark), `MarkWatchedThroughAsync` and `MarkSeasonWatchedAsync`. A new way of marking must return it too.

- **Wording** (`SeriesCaughtUp.Sentence(today)`): ended, "You've finished {series}."; continuing with a regular episode not released yet (the soonest by moment), "You're up to date with {series}. Next episode S03E04 on Fri, Oct 9." (through `DisplayDate`); otherwise "You're up to date with {series}. We'll let you know when a new episode airs."
- **One toast per action.** A single mark's toast becomes the sentence. A mark that has an Undo (season, "this and earlier", the Dashboard's one-tap) keeps its own sentence and its Undo and adds this one: "Marked 8 episodes as watched. You've finished Chernobyl." Undo removes the batch as before.
- **Rate it**: for a finished series the user has not rated (one `GetRatingAsync`, only in that case).
- **Cost and failure**: one extra query per mark (the user's watched ids for the series; the aggregate is already cached). The check is best-effort: if it fails the mark is still recorded and the ordinary toast is shown.

**A mark puts the series in the library.** Marking anything watched adds the series to the user's library when it is not there yet, from whatever page the mark came: `WatchProgressService.EnsureInLibraryAsync` runs after every successful mark, and each marking method's result carries `AddedToLibrary` (the series' name when this mark added it, else null). The page says so in the same toast: "Marked S01E03 as watched and added Silo to your library." (Episode Details names the episode; Series Details says "the episode" or the count), followed by the caught-up sentence when both apply. It only ever adds: unmarking, undoing a bulk mark and "mark season unwatched" never take a series out of the library, and a refused mark or a season with nothing left to mark adds nothing. Best-effort: if adding fails the watch is still recorded. Removing a series is only the "Remove from library" action on Series Details. Nothing else marks episodes: Favorites and notifications only link to them, the Dashboard's cards exist only for series already in the library, and the IMDb import marks movies, not episodes.

**Stopped watching.** A user can say they stopped watching a series without removing it: `tracked_series.stopped_utc` is set (null means watching). The series keeps its place in the library and every watch, like, rating and notification; it only leaves what says "there is something for you to watch".

- **One place decides it**: `SeriesLibraryStateRule` (`Services/WatchTracking/SeriesLibraryState.cs`). `IsStopped(tracked)` is the definition; `Of(aggregate, progress, stopped)` returns `SeriesLibraryState.Stopped` before it looks at progress; `Followed(trackedSeries)` is the library without the stopped series; `CanStop(state)` says whether "Stop watching" is offered. Nothing else reads the column to decide anything.
- **Left out of**: Continue watching on the Dashboard and Watching in the Library; the "haven't watched in a while" group (stopped beats dormant, and a season premiere never brings a stopped series back: it never reaches `ContinueWatchingOrder.Arrange`); new-episode notifications (`ITrackedSeriesRepository.GetUserIdsTrackingAsync` returns only users who have not stopped); all three sections of the weekly digest (`DigestComposer` builds from `Followed`, so the series is not even read); and, on the Dashboard, Upcoming and the "Airing this week" and "Unwatched episodes" counts, which are also about what there is to watch. The Dashboard's "Tracked series" count still includes it.
- **Still counted**: Stats keeps every watch of a stopped series (totals, chart, top lists, genres), but it is not a "series finished" even when it has ended and everything is watched (`StatsInput.StoppedSeriesIds`), matching the Library, where it is under Stopped and not under Watched. Search badges it "Stopped" instead of "In library"; Favorites, Profile and the sitemap do not look at progress.
- **Stopping** (`IWatchProgressService.StopWatchingAsync`): offered for a series that is Watching or Up to date, so also for a continuing series the user is up to date with. Not for a finished one (`StopWatchingOutcome.Finished`), and stopping twice keeps the first date. From the "⋯" menu of Series Details' action row and from a Dashboard card's menu; both are POSTs with no confirmation, and the toast has an Undo.
- **Resuming** (`ResumeWatchingAsync`): "Resume watching" on Series Details (a plain success toast), the Undo of a stop (an info toast), and **any mark**: marking an episode of a stopped series watched, by every marking path, clears `stopped_utc` (`WatchProgressService.EnsureWatchingAsync`, which also does the add-to-library above), and the result's `ResumedWatching` names the series. The toast says so in the same sentence, combined with the caught-up one when both apply: "Marked S03E04 as watched and resumed watching Silo." `MarkLibraryEffect.Clause` is the one wording for that and for "and added Silo to your library". Best-effort like the add: if the resume fails the watch is still recorded.
- **Unmarking never changes the state**, either way: toggling an episode off, "mark season unwatched" and the Undo of an ordinary mark neither stop a series nor resume one.
- **One exception: the Undo of the mark that resumed.** Undo means "as it was", so pressing Undo on the toast of a mark that resumed a stopped series stops it again with its original date. `ITrackedSeriesRepository.ResumeAsync` hands back the date it cleared (`ResumedSeries`), the mark's result carries it (`ResumedFromStoppedUtc`, on the three results that can have an Undo), `SetSuccessToastWithWatchedUndo(..., resumedFromStoppedUtc:)` puts it in the Undo form as ticks (`stoppedStamp`), and `OnPostUndoWatchedAsync` calls `IWatchProgressService.RestoreStoppedAsync` after the batch is removed. It restores only when the undo removed something and the series is not stopped at that moment (a newer stop keeps its date), and the toast then adds "You've stopped watching the series again." A new marking path with an Undo must pass the date on. A single toggle has no Undo toast, so unticking the episode that resumed a series leaves it resumed.
- **Writes** are atomic updates (`TrackedSeriesRepository.StopAsync` / `ResumeAsync`, `ExecuteUpdateAsync`, which set `updated_utc` themselves). The date comes from `TimeProvider`.
- **A new place that lists series by progress, or tells the user about new episodes, must start from `SeriesLibraryStateRule.Followed` (or pass `stopped` to `Of`).**
- **Nothing new to delete**: the column is on `tracked_series`, which account deletion already empties; "Remove from library" (on Series Details only; the Library page has no remove handler) deletes the row, so a series added again starts out as watching.

**Remove from library deletes only the `tracked_series` row** (`TrackedSeriesRepository.RemoveAsync`; no other table references it). The user's episode watches, likes, ratings, notifications and the `notified_episode` ledger for the series all stay, and the confirmation says so ("Your watch history is kept, and comes back if you add the series again"). Watches of a series that is no longer tracked are still in Stats' totals, chart and top lists (never in "series finished") and still show as ticks on its Series Details page; the Library, the Dashboard, the digest and the notification job start from the tracked rows, so the series is in none of them.

**Watch source.** `WatchedUtc` is when a watch was *marked*, which is not always when the title was watched, so every watch row also records how it was written (`WatchSource`, stored as its name in `source`):

| Source | Written by | Its date counts as a watch date |
|---|---|---|
| `Single` | One episode or movie marked on its own: the toggles, the Dashboard's one-tap mark, "Mark as watched" on a movie, and the episode the user clicked in "mark this and earlier" | yes |
| `Bulk` | "Mark season watched" (every row, even when one is left), and the earlier episodes swept in by "mark this and earlier" | no |
| `Import` | A movie marked watched by the IMDb import | no |
| `Unknown` | Rows from before the column existed (2026-10-02) that the migration did not recognise as either of the above; also the column's default | yes |

`WatchSourceExtensions.IsDated` is that last column. The `WatchSource` migration classified the existing rows once: a movie watch within a minute of one of the user's import rows that resolved to it became `Import`; three or more episode watches by one user in one series, each within two minutes of the one before, became `Bulk`; everything else stayed `Unknown`. The source is set by the write paths (`IEpisodeWatchRepository.MarkWatchedAsync` is always `Single`; `MarkWatchedRangeAsync` takes the source and, optionally, the one clicked episode that is `Single` regardless; `IMovieWatchRepository.ToggleAsync` and `IMovieTrackingService.MarkWatchedAsync` take it). A new way of marking something watched must pass the right one. A batch still shares one `WatchedUtc`; the undo goes by its `batch_id`, so the source plays no part in it.

**Stats** (`Services/Stats/`, page `Pages/Account/Stats`). `IStatsService.GetAsync(userId)` returns a `UserStats` record, computed by the pure `StatsBuilder.Build(input, today, window)`; Profile's watch-time figure is its `Totals.WatchTime`, so the two cannot disagree.

- **Two rules.** Totals and the top lists count *every* watch row. The monthly chart counts only rows whose source `IsDated`, in the UTC month of `WatchedUtc`; `StatsUndated` says how many were left off, and the page says so under the chart.
- **Totals**: watch time, episodes (every `episode_watch` row, specials and movie-flagged entries included: time is time), movies (every `user_movie_watch` row), and series finished: tracked series that `SeriesLibraryStateRule` calls `Finished`, exactly the series under Watched in the Library (so not one the user stopped watching).
- **Runtime**: an episode's own, else the series' average (also for a watched episode the aggregate no longer lists), else nothing; a movie's own. OMDb's runtime is never used (it is unreliable).
- **Month by month**: the current UTC month and the eleven before it (`StatsWindow.LastTwelveMonths`; `StatsWindow.CalendarYear` exists for a year-in-review page nobody has built). Totals are all-time whatever the window.
- **Most watched series**: top 5 by watch time, then episodes, then name; a series without a cached record has no name and is not listed.
- **Genres**: TheTVDB's, for series and movies alike; top 6 by watch time. A title counts in full under each of its genres, so they add up to more than the total. Labels that say what format a title has, not what it is about, are left out: `StatsBuilder.FormatLabels` (today "Mini-Series") is the one list, and it applies to the statistics only; Series Details still shows the chip. `StatsGenreCoverage` says how many watched titles have genres at all (see "Genres" under TheTVDB in section 7), and the page says "Based on N of M titles" until that is all of them.
- **Ratings**: how many titles got each value 1–10 (series, episodes and movies together), the count and the average, from `IRatingRepository.GetValueCountsAsync`.
- **No streaks.** Bulk marking would break them for people who watch every week and catch up their marks monthly. Decided 2026-10-02.
- **Zero API calls.** Metadata is read with `GetCachedSeriesAggregateAsync` / `GetCachedMovieAggregateAsync` only (Redis, then the Postgres snapshot), at most 16 reads at a time. A title in neither is still counted, with no length, name or genre, and `StatsGaps` reports it; the page ends with one sentence about what was counted without a length. A watched series is always cached (marking needs the aggregate). An imported movie is cached only once the Library or its own page has been opened: the importer matches through TheTVDB's remote-id search, which returns a base record, and caching the full movie would cost two more requests per row, so it does not.
- **No per-user cache.** Measured 2026-10-02 on a review clone (Debug build, 945 episode watches in 18 titles): about 10 ms; with 500 watched movies added, about 70 ms the first time (Redis cold, 500 snapshot reads) and 21–29 ms after. The threshold for adding a Redis cache was 100 ms. If one is ever added, key it on a fingerprint of the user's rows and remove the key in `DeleteAccountAsync`.
- **Nothing new to delete.** Stats adds no table; `source` is a column on two tables account deletion already empties.

**Bulk marks and undo.** `MarkSeasonWatchedAsync` / `MarkSeasonUnwatchedAsync` act on one season of the aggregate. **An undo identifies a batch by its id, never by time.** Every marking action writes an id on each row it inserts (`episode_watch.batch_id`, a new `Guid` per action): `EpisodeWatchRepository.MarkWatchedRangeAsync` gives one id to all of its rows, so a season, a "mark this and earlier" (the clicked episode, a `Single` row, and the earlier ones, `Bulk`, alike) and the Dashboard's one-tap mark are each one batch, and `MarkWatchedAsync` gives its one row an id of its own. The id comes back as `WatchedBatch.Id`; the toast's Undo form posts it as `batch` (TempData key `UndoWatchedBatchKey`), and `UndoWatchedBatchAsync` deletes the user's rows in that series that carry it, nothing else. A form without a usable id (a toast rendered before 2026-11-13 posted the batch's timestamp as `stamp`; an empty or unparsable id) gets "Nothing left to undo." (`DetailsModel.NothingToUndo`) and changes nothing, and a toast cookie holding the old key gets no Undo button. The id crosses the redirect as TempData and comes back from the cookie as a `Guid`; until 2026-11-22 the toast read it `as string`, so no Undo button was drawn at all ("Toasts" in section 4). Rows from before the column keep `batch_id` null, and no undo reaches them. No index: the delete also filters on user and series, and the `(user_id, series_tvdb_id)` index narrows it to one user's watches of one series before `batch_id` is checked (`BulkWatchUndoTests` asserts the plan). Until 2026-11-13 the undo matched the batch's `WatchedUtc`, truncated to the millisecond, and so also deleted any other watch of the user's in that series stamped in the same millisecond: a single mark whose untruncated time fell exactly on that millisecond, or a second batch in it (seen as `EpisodeWatchRepositoryTests` failing about once in 375 runs). Nothing else identifies rows by a timestamp: the stopped-state restore writes its date back as a value, and movie watches and the import only sort by theirs. The rows of a batch still share one `WatchedUtc`, which is a fact about when they were marked and no longer a key; `EpisodeWatchRepository` takes it from an optional `TimeProvider` (the system clock in the app, a fixed one in tests).

**Movies** are on the watchlist (`TrackedMovie`) or watched (`UserMovieWatch`), never both, and independently liked or rated. `IMovieTrackingService` (`Services/WatchTracking/MovieTrackingService.cs`) owns that rule: marking a movie watched takes it off the watchlist, a watched movie can't be added, and un-watching does not put it back. Page models and the importer call the service, not the two repositories, for writes.

## 6. Data access

- **ORM**: EF Core 10 on PostgreSQL via Npgsql. One context, `Infrastructure/Persistence/AppDbContext.cs`. No Dapper or raw SQL.
- **Configuration**: one `IEntityTypeConfiguration<T>` per entity in `Persistence/Configurations/`, applied with `ApplyConfigurationsFromAssembly`. Tables are singular snake_case, columns snake_case, enums stored as strings, timestamps `timestamp with time zone`.
- **Context options** (`AddPostgres`): shared `NpgsqlDataSource` with `EnableDynamicJson()`, `SplitQuery` by default, and `MultipleCollectionIncludeWarning` raised to an exception.
- **Audit timestamps**: an entity opts in by implementing `IHasAuditTimestamps` (`CreatedUtc`, `UpdatedUtc`); `SaveChanges`/`SaveChangesAsync` stamp every tracked one. Eleven entities do. `ExecuteUpdateAsync` and raw SQL bypass the change tracker, so those set `UpdatedUtc` themselves. `AuditTimestampTests` fails if an entity has both columns but not the interface.
- **Two ways to get a context**:
  - Repositories and `EpisodeOmdbSnapshotStore` inject the scoped `AppDbContext`. Calls on it must stay sequential.
  - `TvdbSnapshotStore`, `OmdbSnapshotStore`, `MovieOmdbSnapshotStore` and `SitemapService` use `IDbContextFactory` and open a context per call, so callers may run them under `Task.WhenAll`.
- **Repositories** (`Persistence/Repositories/`): interface + sealed implementation, return domain models or small records, reads use `AsNoTracking`. Exception: `IAppUserRepository` returns `AppUserEntity`. No page model touches `AppDbContext`. An expected outcome is a return value (`AddAsync` returns `false` for "already there"), not an exception for the caller to pattern-match.
- **Concurrency idiom**: check, insert, then catch `DbUpdateException` whose inner `PostgresException` is `UniqueViolation` and treat it as success. The catch must also take the losing row out of the context (`Entry(entity).State = EntityState.Detached`, or `ChangeTracker.Clear()`), otherwise the next `SaveChanges` on the same scoped context retries the insert and throws. Atomic state changes use `ExecuteUpdateAsync` (`LoginTokenRepository.MarkConsumedAsync`).
- **Migrations**: generate with the CLI; never hand-write (the `Designer.cs` and snapshot must match). They run automatically at startup (in Production never on an empty database; see "Before serving" in section 3). There is no design-time factory, so `dotnet ef` builds the host through `Program.cs`.
- **Data-only migrations**: still generate the (empty) migration with the CLI, then add `migrationBuilder.Sql(...)` to `Up`; see `ClearSentEmailBodies`. To try one against real rows without touching dev data, create a scratch database on the local Postgres container and pass `--connection` to `dotnet ef database update <previous migration>`, seed, then update to latest. On macOS the `dotnet ef` tool leaves a stray `Recall.Web/bin\Debug/` folder (literal backslash) that `.gitignore` does not match; delete it after running any `dotnet ef` command.
- **Seeding**: none. In local dev the hardcoded dev user row must be inserted by hand (see section 12).

**Query patterns worth knowing before optimizing**

- No classic N+1 over navigation properties; no `Include` calls anywhere.
- `Dashboard`, `Library`, `Favorites` and `NewEpisodeNotificationTimer` load one full `SeriesAggregate` per tracked/liked/watched series with `Task.WhenAll` on every request: a Redis GET (compressed, about a quarter of the JSON) plus decompression and deserialization of every episode and character. This is fine as it stands; see the note under TheTVDB in section 7. `Profile` and `Stats` (both through `StatsService`) do the same for every watched series and movie, from the caches only and 16 at a time.
- A Stats page load (and a Profile load) sends three queries for one user's rows: every episode watch, every movie watch, and the rating counts (`GROUP BY value`). Each is served by an existing index that leads with `user_id` (bitmap index scan, 0.06–0.32 ms for one user's 1,000 watches, 200 movies and 100 ratings among 60 users'; measured 2026-10-02, and `StatsQueryTests` asserts the plans). `source` is not indexed: it is read with the user's rows and judged in memory.
- The activity query behind the continue-watching order (`GROUP BY series_tvdb_id` with `max(watched_utc)` over one user's `episode_watch` rows) is served by the existing `(user_id, series_tvdb_id)` index: a bitmap index scan and a hash aggregate, 0.35 ms for one user's 1,000 watches in a table of 60,000 (measured 2026-10-02 in the PostgreSQL suite, where `ContinueWatchingQueryTests` asserts the plan). Adding `watched_utc` to the index was considered and not done: it would only save the heap fetches of one user's rows.
- `NewEpisodeNotificationTimer` loops series, then users, with one watched-ids query and one or two notification queries per pair.
- The sitemap is capped at 50,000 URLs (`SitemapModel.MaxUrls`): `SitemapService.GetCachedContentAsync` fills series, then movies, then episodes with the room left, most recently refreshed first.
- `RatingRepository.GetSummaryAsync` gets `COUNT` and `AVG` in one grouped query.
- `WatchlistImportRepository.RecalculateJobProgressAsync` counts items per status with a grouped query.
- The notification bell's unread `COUNT` (every signed-in page) is index-backed on `notification(user_id, …)`; it was checked with `EXPLAIN` and left alone.

## 7. External integrations

### TheTVDB (v4 API)

Plan: the **free tier, which requires attribution**. The attribution is the "Metadata provided by TheTVDB" link (to `https://thetvdb.com`) and logo in the footer of `_Layout.cshtml`, which every page that shows TheTVDB data uses. The text must stay visible at every screen width; it may wrap or shrink but is never hidden.

- **A lighter per-series summary was measured and rejected** (2026-10-01). With the dev user tracking 58 series (10,565 episodes), Dashboard, Library and Profile took 20–25 ms of server time reading full aggregates; a cached projection without overviews and characters saved 3–6 ms per request, which did not justify a second cache entry per series. Everything reads the aggregate. Revisit only if these pages get measurably slow.

- `Services/External/TheTvDb/TheTvDbApiClient.cs` is pure transport: typed `HttpClient` whose 8 s timeout bounds one attempt (body included), bearer token attached per request.
- `TheTvDbClientState` **must stay a singleton**. It holds the cached token and a `SemaphoreSlim(5)` throttle shared by all client instances. On a 401 the client passes the specific stale token back, so only one of several racing requests re-authenticates; the request is resent once inside the same attempt.
- Non-success responses throw `TheTvDbApiException`.
- **Resilience** (`Infrastructure/External/ExternalHttpResilience.cs`, `Microsoft.Extensions.Http.Resilience`). Retries happen on network errors, timeouts, 408, 5xx, and for TheTVDB on a 429 whose `Retry-After` is at most 2 s; waits between attempts are capped at 2 s.
  - **TheTVDB**: 2 retries, run by `TheTvDbApiClient.SendAsync` through a keyed `ResiliencePipeline<HttpResponseMessage>`, *outside* the throttle. Each attempt takes its own slot, so a request backing off does not occupy one of the five slots, and time queueing for a slot counts against no timeout. Worst case 3 × 8 s + 2 × 2 s = 28 s, inside the 30 s budget (`TheTvDbOverallBudget`).
  - **OMDb**: an ordinary resilience handler inside the `HttpClient`: 1 retry, never on 429, 8 s per attempt, 20 s client timeout overall. The retry takes its own permit from `IOmdbRequestBudget` and is skipped when none is left, because every request OMDb receives counts against the daily limit.
  - Changing an attempt timeout or retry count means changing the constants in that file; tests assert the worst case still fits. Do not move the TheTVDB retries into a handler: that puts them back inside the throttle slot.
  - **Names in log lines**: Polly names a line's source pipeline/instance/strategy. The pipelines are `thetvdb` and `omdb`, both with instance `standard`; the strategies are `Retry` and (OMDb) `AttemptTimeout`, so a line reads `thetvdb/standard/Retry`. A new pipeline or strategy gets a name the same way (`ExternalHttpResilience` constants).
  - **What they log** (category `Polly`, held at Warning, see "Logging" in section 10): nothing for a call that succeeds first time. A failed attempt that will be retried is a Warning "Execution attempt … Handled: 'True'" followed by a Warning "Resilience event occurred. EventName: 'OnRetry'". The last attempt of a TheTVDB call that still fails is an Error "Execution attempt … Handled: 'True'", and the client adds its own Warning ("TheTVDB request failed. StatusCode: 503"). OMDb's last attempt is not "handled" (its retry rule says no once the retry is spent, to spare the budget), so Polly logs it at Information, which is filtered; the failure is logged at Warning by the caller (the OMDb jobs and Episode Details catch it and log with the exception).
- `Services/TheTvDbService.cs` owns the read path through `GetLayeredAsync<T>`: **Redis → Postgres snapshot → API**. A database or API hit is written back up. Nulls are not cached.

| Resource | Redis key (instance prefix `tvdb:`, `TvdbCacheKeys`) | Redis TTL | Postgres table |
|---|---|---|---|
| Series aggregate | `series:aggregate:v2:{id}:{lang}` | 7 d ±10% | `cached_series_aggregate` |
| Movie aggregate | `movie:aggregate:v2:{id}:{lang}` | 7 d ±10% | `cached_movie_aggregate` |
| Series extended | `series:extended:v3:{id}` | 7 d ±10% | `cached_series_extended` |
| Episode extended | `episode:extended:v3:{id}:{lang}` | 7 d ±10% | `cached_episode_extended` |

Nothing of OMDb's is in Redis: its snapshots are read from Postgres only.

- **Redis format** (`Infrastructure/Caching/CachePayload.cs`): a value is a format byte, the JSON's length (4 bytes), then the JSON (`RecallJsonOptions.Web`) compressed with Brotli at quality 4. Measured 2026-11-14 on the dev snapshots (10 series, 4 movies, 25 episodes): series aggregates shrink to 24% (the largest, 221 KB, to 58 KB), movies to 17%, episodes to 42%; the whole set takes 180 KB of Redis memory instead of 678 KB. GZip at `Optimal` is the same size and slower to compress; Brotli at quality 11 is a fifth smaller but takes 180 ms for the largest series. Compressing the largest takes 1.3 ms and decompressing 0.3 ms, and a full read of it from Redis is faster than before (1.6 ms against 2.3 ms on loopback). A value that is not in the format, or does not decompress or deserialize, is a miss. The Postgres tables keep plain `jsonb`.
- **Key versions** name the format of the value. Bump them (`TvdbCacheKeys`) when the stored bytes change meaning, or when anything other than `TheTvDbService` rewrites a snapshot payload in Postgres (a data migration, a seed: the UI review flushes its Redis database after seeding for this reason). Old entries are then never read and expire on their own. The step to v2/v3 on 2026-11-14 was the compression.
- **Lifetimes: 7 days for everything, not sliding.** The lifetime decides nothing about freshness: a miss is served from the Postgres snapshot, never from TheTVDB, and every refresh (`Refresh*ByIdAsync`) and the episode still backfill rewrite the Redis entry along with the row, and after an outage, when a refresh may have rewritten a row without its entry, the whole cache is cleared (next point), so an entry is never older than its row. A short lifetime only means more misses and more writes; until 2026-11-14 it was 12 h for anything still changing (7 d for ended series and released movies), and production keys lived about 15 h on average with 27% of reads missing. Sliding expiry is not used because it adds a write (an `EXPIRE`) to every read. Memory is bounded by Redis (`maxmemory 256mb`, `allkeys-lru`, see section 12). `TheTvDbService.RedisLifetime` holds the value.
- **Redis is only a copy, and never fails a request** (`DistributedCacheJson`). When Redis is down or failing, a read is a miss (served from Postgres, with no TheTVDB request) and a write is skipped; the caller's own cancellation still propagates. After a failure Redis is bypassed for 30 s (`DistributedCacheJson.BypassFor`), and one Warning is logged per outage. The connection uses `BacklogPolicy.FailFast` (`RedisConnection.Options`): with the default policy each call waited the 5 s async timeout while Redis was unreachable; now only the first connection attempt after start waits (`connectTimeout`, 5 s). Once Redis is back, reads refill it. Checked on 2026-11-14 with the app on a clone of the dev database, Redis stopped and TheTVDB pointed at a closed port: every page answered 200 with no TheTVDB request, and Redis held its entries again within seconds of starting.
- **The server is Valkey** (`dhi.io/valkey:9.1`, Docker's hardened image, in `compose.prod.yml` since 2026-11-22; before that `redis:7`, which had become 7.4 under the RSALv2/SSPL licences. The server switches when the owner applies the README's "Switching production to Valkey"). It speaks the Redis protocol and reports itself as Redis 7.2.4, so the client is unchanged: `Microsoft.Extensions.Caching.StackExchangeRedis` over StackExchange.Redis 2.7.27, and the names in code and configuration still say Redis (`REDIS_CONNECTION`, `RedisCacheClearer`, the compose service `redis`). Nothing Recall sends is Redis-only: the distributed cache's hash commands, and `SCAN` and `UNLINK` from the clearer. The hardened image keeps **protected mode** on, which refuses every client that is not on loopback while no password is set; production therefore runs it with `--requirepass` (`VALKEY_PASSWORD`, and `password=` in `REDIS_CONNECTION`), and local and test containers with `--protected-mode no` (local bound to 127.0.0.1). The trap: a refused app is not an error anywhere visible except the app's log, since Recall falls back to Postgres (above) and `valkey-cli` inside the container, being loopback, still answers. After any change to the cache's setup, check the app log for "Redis read failed". The healthcheck is `valkey-cli -e ping` with `VALKEYCLI_AUTH`: without `-e`, `valkey-cli` exits 0 on `NOAUTH`.
- **After an outage the cache is cleared once.** While Redis is skipped, a refresh rewrites the Postgres row but not its Redis entry, and an entry from before or during the outage would otherwise be served for the rest of its week. So when the bypass after a failure ends, the first caller removes every key under the `tvdb:` prefix (`ICacheClearer`, `RedisCacheClearer`: `SCAN` page by page and `UNLINK` in batches of 500, in the connection string's default database; never `KEYS`, `DEL` or a flush, so another prefix or database is untouched) before anything is read from or written to Redis, and logs one Information line: "Redis is reachable again after an outage; removed N cache key(s) written before or during it." The clear is also the check that Redis is back: if it fails, the bypass starts again and the next caller after it tries again. Other callers skip Redis while it runs, and the cache then refills from Postgres. A run with no failure never clears anything. Every failure counts, including one transient timeout, which then costs a clear and a refill from Postgres (no TheTVDB requests). The clearer has its own connection, made on first use (`RedisCache` keeps its connection private), configured like the cache's. A Redis that hangs rather than refusing (overloaded, frozen) still costs the one call that finds it the 5 s timeout. Checked on 2026-11-14 the same way as above, with the Redis container paused (it keeps its keys, unlike a restart without persistence): the first request waited 5.5 s and was served from Postgres, and the first request after unpausing and the 30 s logged "removed 12 cache key(s)", left a key outside the prefix alone, and the cache refilled.

- **The Postgres tier has no staleness check on read.** A row is served until something explicitly refreshes it: `Refresh*ByIdAsync` or the hourly jobs, which revisit keep-updated aggregates after 12 h and all others after 30 d. The read path's `Save*` methods are insert-only; only the refresh path upserts. A mapping change therefore does not reach already-cached rows until they are refreshed, which can take up to 30 days plus queue time, unless the mapping version is bumped (series only, next point).
- **Mapping version** (series aggregates). Every `cached_series_aggregate` row records the version of the DTO-to-aggregate mapping that wrote it (`mapping_version`, from `SeriesDataDtoMappings.AggregateVersion`). The refresh queue (`GetAggregatesNeedingRefreshAsync`) puts rows below the current version first, whatever their age, within the same cap of 10 per hour; a refresh brings a row up to date, so when none are left the job is back to its age-based order. Version 1 is the mapping that keeps genres; rows cached before it are 0. **When `ToAggregate` starts keeping a field that cached rows lack, bump `AggregateVersion`**, unless the field is cosmetic enough to wait for the normal schedule. The one such field so far is the network (`SeriesAggregate.Network`, 2026-11-23: the extended record's `originalNetwork`, else `latestNetwork`), for Series Details' meta line and facts: a backfill would have held back the 12-hour refreshes of continuing series for hours, so it was added without a bump, and a row cached before it shows no network until it is next refreshed (12 h for a continuing series, up to 30 days for others). The version is about what wrote the row, not about what the series has: a series TheTVDB lists no genres for is done after one refresh. While a backfill runs, age-based refreshes wait behind it: (rows to backfill ÷ 10) hours.
- **What a series costs: three requests, whatever its episode count.** `TheTvDbApiClient.FetchSeriesAggregateAsync` (behind both the first fetch of an uncached series and every refresh) sends the extended record (`series/{id}/extended?meta=episodes`), the series translation, and the translated episode list (`series/{id}/episodes/default/eng`, 500 episodes per page, so a fourth request only past 500 episodes). The extended record has every episode field but names and overviews in the series' original language; the translated list supplies those two in English and nothing else is taken from it. An episode the list lacks, or a blank translated field, keeps the original; if the list fails the aggregate is still built, with original names. **Rule: nothing that fetches or refreshes a series may make a request per episode.** Until 2026-10-02 the service translated every episode without a `cached_episode_extended` row with its own request, on every refresh: 16 to 465 requests per series on the dev database, 956 for its ten series, against 30 now (measured by running the job on a clone: "31 TheTVDB request(s) this run", one of them the login; the refreshed aggregates had the same fields as before). A single episode's own endpoints (`episodes/{id}/extended` and its translation, two requests) are for what exists nowhere else, such as the IMDb id, and are called lazily by Episode Details and by the still lookup of the Dashboard and Favorites cards (`GetEpisodeArtAsync`, only for an episode whose still the aggregate lacks), and by the capped episode tier of `UpdateTvDbInfoTimer` (25 cached episodes a run), never by a series fetch.
- **Counting requests**: `TheTvDbRequestMeter.Start()` counts the requests sent to TheTVDB by the code awaited inside it (retries, the resend after a 401 and the login included; it follows the async flow, so concurrent work elsewhere is not counted). `UpdateTvDbInfoTimer` logs its total every run at Information: "UpdateTvDbInfoTimer: N TheTVDB request(s) this run: A for S series, B for E cached episode(s)." Expect about 3 per series and 2 per episode; much more means a per-episode request is back.
- Language is hardcoded to `eng`. A series' episode names and overviews come translated from the episode list (above), not episode by episode.
- **Image URLs**: TheTVDB returns absolute and relative paths inconsistently. Every image field goes through `ArtworkUrl.Normalize` at DTO → domain mapping time, and again on every service read via `DomainImageNormalization.WithNormalizedImages()` so old cached rows heal. A new image-bearing field needs both.
- **Stills that arrive late** (`StillRecheck`, in `ITvdbSnapshotStore.cs`). A still usually reaches TheTVDB days after an episode airs, sometimes weeks, and for many episodes never. A cached episode row (`cached_episode_extended`, `has_image` false) whose episode has aired is rechecked by the episode tier of `UpdateTvDbInfoTimer`: once a day while it aired within 30 days, once a week up to 90 days, then no longer for the still's sake (the general 30-day refresh of every row still looks at it). The schedule goes by the air date, so an episode cached before it aired, or refreshed many times as "TBA", is not penalised (until 2026-10-02 a counter gave up after five imageless refreshes, about 2.5 days, counting refreshes from before the air date). The rechecks share the tier's cap of 25 episodes a run and add no budget: at most 1,200 requests a day for the whole tier, as before. Expected cost: 2 requests a day per aired, still-less cached episode in its first 30 days, 2 a week after that, about 80 over the 90 days if the still never comes. Which episodes have a row: the ones someone has opened, liked, or has as their next episode without a still (those pages read the record, see "An episode's image"). **Series that rarely have stills are skipped**: when the series' cached aggregate shows a still for fewer than `TheTvDb:StillRecheckMinStillPercent` percent (default 10) of its aired regular episodes, and at least `TheTvDb:StillRecheckMinAiredEpisodes` (default 10) have aired, its episodes are not rechecked for a still at all and keep the background-art fallback (Bonde söker fru has stills for 2 of 177). 0 percent turns the rule off; an episode whose series is not cached is rechecked as usual; the stale and "TBA" refreshes are unaffected. The two counts are columns of `cached_series_aggregate` (`aired_episode_count`, `aired_still_count`), written by `TvdbSnapshotStore.StillCoverage` whenever the aggregate is saved or refreshed, so "aired" is as of that moment. The other way round is free: a series refresh copies any still the aggregate has into the episode rows that lack one (`BackfillEpisodeImagesFromAggregateAsync`).
- **Background art**: `SeriesAggregate.BackgroundUrl` is the thumbnail of the best-scored artwork of type 3 (TheTVDB's 16:9 series background, "fanart") from the extended record's `artworks`; `MovieAggregate.BackgroundUrl` the same of type 15 (a movie's background), added 2026-11-23, so a movie row cached earlier has none until it is refreshed (movies have no mapping version). It was added on 2026-10-02, so (see the staleness note above) a row cached earlier has none until it is refreshed: within 12 h for a keep-updated series, up to 30 days for the rest.
- `SearchAsync` and `ResolveByRemoteIdAsync` are not cached.
- **Genres**: `SeriesAggregate.Genres` is TheTVDB's genre list, the same vocabulary `MovieAggregate.Genres` has always had. It was added on 2026-10-02; a series row cached earlier has none until it is refreshed, which the refresh job does ahead of everything else (see "Mapping version" above). Series Details shows TheTVDB's genres and falls back to OMDb's (a different vocabulary: "Sci-Fi" for "Science Fiction") only while the series has none; Stats never uses OMDb's.
- `GetCachedSeriesAggregateAsync` and `GetCachedMovieAggregateAsync` are the reads that never reach the API: the same Redis and Postgres tiers, and null when neither has the title. Use them for work that must not spend quota: background jobs (the weekly digest) and pages that must cost nothing per view (Stats, Profile).

### OMDb

Plan: the **free tier, 1,000 requests a day**. `Omdb:MaxRequestsPerDay` defaults to 900 to leave headroom.

- `Services/External/Omdb/OmdbApiClient.cs`: typed client, 20 s overall timeout (8 s per attempt, one retry), API key in the query string, returns `null` for "not found". It has no cache of its own.
- Snapshots live in `cached_series_omdb`, `cached_movie_omdb` and `cached_episode_omdb`, refreshed at most every 30 days. A row with a null payload records "checked, nothing found".
- **Types**: `OmdbSeries`, `OmdbMovie` and `OmdbEpisode` (`Domain/Omdb/`) all derive from `OmdbTitle`, whose `[JsonPropertyName]` values are also the storage format of the three `payload` columns. Rows cached before the types were split still load (unknown keys are ignored). Do not rename a JSON property there; adding one is safe. The client exposes `GetSeriesAsync` / `GetMovieAsync` / `GetEpisodeAsync`.
- Series and movies are enriched proactively by hourly jobs. **Episodes are enriched lazily on the request path**, the first time a *signed-in* user opens `Episodes/Details` (`DetailsModel.LoadOmdbAsync`). An anonymous request only ever reads the cached snapshot.
- Every request that reaches OMDb must be covered by a permit from the singleton `IOmdbRequestBudget` (`FixedWindowRateLimiter`, default 900/day via `Omdb:MaxRequestsPerDay`). Call sites take one before calling the client; the client's retry takes its own. A new call site must do the same.

`Services/Authentication/TurnstileVerifier.cs` posts to `siteverify` from the login page, with a 10 s timeout and no retry. It is disabled when either key is blank and fails closed on any failure: a rejected token, a network error, an error status, an unreadable body, or a timeout. Only the caller's own cancellation propagates.

### Web Push

Browsers' push services: Google FCM (Chrome, Android, Samsung Internet, Opera, Brave), Apple (Safari on iPhone, iPad and Mac, iOS 16.4+ and only from a Home Screen app), Mozilla (Firefox) and Microsoft WNS (Edge). ## 8. Authentication and authorization

- No ASP.NET Core Identity, external providers or JWT. Cookie authentication only (`AddCookieAuthentication`): cookie `Recall.Auth`, 30-day sliding expiry, HttpOnly, SameSite=Lax, Secure in Release builds. Login and access-denied paths are both `/Account/Login`.
- **Cookie revalidation**: `Infrastructure/Authentication/RecallCookieEvents.cs` (`options.EventsType`) re-reads the user row at most every 5 minutes per session. A missing user is signed out; a changed username, email or role is reissued into the cookie. The last-check time is stored in the cookie's own properties. A database error keeps the session and retries on the next request. `RecallPrincipal.Create` is the single definition of the claim set; use it when issuing a cookie.
- **Request a link** (`PasswordlessAuthService.RequestLoginAsync`): normalize email → optional allowlist (`Login:AllowedEmails`; empty means open registration) → `ILoginAbuseGuard` per-address daily cap and site-wide hourly cap → get or create the user → per-user resend cooldown → invalidate earlier tokens → store the SHA-256 hash of a 32-byte random token and of a 6-digit code → reset the address's wrong-code count → queue the email (link and code). The page shows the same "link sent" result in every case.
- **Redeem** (`RedeemAsync`, `Pages/Account/Verify`): look up an unconsumed, unexpired hash, then `MarkConsumedAsync` (atomic `UPDATE … WHERE ConsumedUtc IS NULL`). The result of that update is checked so two simultaneous redemptions cannot both succeed. Then `SignInAsync` with `NameIdentifier`, `Name`, `Email` and `Role` claims.
- **The sign-in code** (`SignInCode`, `RedeemCodeAsync`, `LoginModel.OnPostVerifyCodeAsync`). Every sign-in email also holds a 6-digit code, shown as "482 913", for where the link doesn't open: a Home Screen app on an iPhone keeps its own cookies and the link opens Safari, so without it nobody could sign in there, or turn on push. The code is a second way to redeem the same `login_token` row, so it has the link's lifetime and using either consumes both. Only `SignInCode.Hash` is stored (SHA-256 of "{token id}:{code}"), compared with `CryptographicOperations.FixedTimeEquals`. The page's "Check your inbox" state posts the address the email went to with the code (spaces ignored), so it needs no cookie of ours but the antiforgery one. Failures: a wrong code, an expired one, a malformed one and an unknown address all return `InvalidOrExpired` and the page shows one message. A wrong code against a live token is counted in one atomic update (`RecordWrongCodeAsync`) that consumes the token at the fifth (`SignInCode.MaxWrongAttempts`); `ILoginAbuseGuard` also counts wrong codes per address in memory (reset when a new email goes out or the code works), so an unknown address locks out after five exactly like a known one (`TooManyAttempts`, "request a new email") and the answers never show which addresses have accounts. Code POSTs are rate limited per IP in their own bucket of the `login-email` policy (`LoginCodePermits`, 10 per 5 minutes, chosen by `?handler=VerifyCode`, since a page has one policy for all its handlers). Five guesses per token and five emails per address a day leave a guesser at most 25 tries in a million per address a day. The hash alone does not resist an offline search of a million codes; it protects a code only for the token's lifetime, which is also all the code is worth.
- **Bot defenses on the login form**: honeypot field, minimum 2 s render-to-submit time, Turnstile, per-IP rate limit on requests for a link (`login-email` policy, `LoginEmailPartition`: 8 POSTs per 5 minutes; page loads are never counted, so reloading cannot lock anyone out; code POSTs have their own 10 per 5 minutes) and a global limiter on POSTs to `/Account/Login` (300 per minute). Both rate-limit policies live in `AddRateLimiting`.
- **Roles**: `User` and `Admin` (`UserRole` enum; `Roles` constants for attributes). Promotion to Admin is a manual database edit.
- **Per-user scoping**: `ICurrentUserService.UserId` (parsed from the claim) is passed into every repository call, and every user-data query filters on `UserId`. There are no global query filters.
- **`DevAuthMiddleware`**: in Debug builds every non-file request runs as a fixed admin (`11111111-1111-1111-1111-111111111111`, `dev-user`, `dev@example.com`). It skips itself when `ASPNETCORE_ENVIRONMENT=Test` and is compiled out of Release. It does not create the user row.

## 9. Background work

Quartz.NET with the default in-memory store, registered in `AddScheduledJobs(configuration)`. Implementations are in `Infrastructure/Timers/`, all `[DisallowConcurrentExecution]`. The hosted service waits for running jobs on shutdown.

| Job | Interval | Work per run |
|---|---|---|
| `UpdateTvDbInfoTimer` | 60 min, on the full hour | Up to 10 series aggregates (about 3 TheTVDB requests each): first those written by an older mapping version (today: without genres), whatever their age; then `KeepUpdated = true` and older than 12 h, or any other row older than 30 d. Within each group tracked series first, then oldest. Then up to 25 episodes older than 30 d, or titled "TBA" and older than 12 h, or aired without a still and due a recheck (daily for 30 days after airing, weekly up to 90, then no more; 2 requests each). Logs the run's TheTVDB request total |
| `UpdateMovieInfoTimer` | 60 min, on the full hour | Up to 10 movie aggregates, same two tiers; movies on a watchlist, watched or liked first |
| `UpdateOmdbInfoTimer` | 60 min, on the full hour | Up to 30 series whose OMDb snapshot is missing or older than 30 d |
| `UpdateMovieOmdbInfoTimer` | 60 min, on the full hour | Same, for movies |
| `MailTimer` | 1 min | Sends up to `Mail:BatchSize` (20) queued emails; gives up after `MaxSendAttempts` (5) |
| `NewEpisodeNotificationTimer` | 60 min | Releases push notifications held for quiet hours whose 08:00 has come. For up to 500 tracked series, notifies each tracking user who has not stopped watching it about episodes released (by moment, see "Released" in section 5) in the last 3 days that they have not watched; one notification per series per user. Then sends one push per device to each user who got a notification (see "Push notifications" in section 5) and logs pushes sent, held and failed. Reads the series only from the caches (`GetCachedSeriesAggregateAsync`) and makes no TheTVDB or OMDb request, so it can run hourly: a notification arrives within an hour of the release moment. A series in neither cache is skipped until a page or the refresh job caches it |
| `WatchlistImportTimer` | 1 min | Resolves up to 15 pending import rows through TheTVDB's remote-id search. A rated movie is marked watched and rated; an unrated movie goes on the watchlist; a series goes into the library (and is rated if the row has a rating) |
| `PruneOldDataTimer` | 24 h (first run 90 s after start) | Deletes rows past their retention period, one `ExecuteDeleteAsync` per category via `IDataRetentionRepository`: login tokens 7 d after they expired or were consumed; emails 30 d after they were sent or gave up; notifications 90 d after they were read; `notified_episode` rows after 30 d; completed import jobs and their items after 90 d; weekly-digest ledger rows after 60 d; push subscriptions 180 d after their last successful push (or their creation). Never touches a queued email, an unread notification or an import still processing |
| `WeeklyDigestTimer` | 60 min (first run 2 min after start) | Does nothing unless `Digest:Enabled` (on in production). When a digest is due, queues it for up to `Digest:MaxPerRun` (default 100; 50 in production) opted-in users not yet dealt with for that week |

The four hourly metadata jobs use Quartz's daily-time-interval schedule, which fires at whole multiples of the interval counted from midnight: on the full hour, not a fixed time after start (their `StartAt` only says from when). The other jobs use simple schedules and do run a set time after start.

`Jobs:Disabled` (a list of job class names, empty by default) keeps a job from being scheduled at all; a name that is not a job fails startup. The UI review instances use it to switch off `WatchlistImportTimer`, `WeeklyDigestTimer` and `UpdateTvDbInfoTimer`. A new job must be added to `ScheduledJobNames` (startup fails otherwise).

There are no other hosted services, queues or message brokers. The email and import "queues" are database tables.

Recall's own categories follow `Default`. **Rule: a framework category that logs once per request, query or outbound call stays at Warning in every environment**; Recall's own Information lines (job summaries, the TheTVDB request count, the push counts, "Refreshed series aggregate …") are kept. `LoggingLevelsTests` holds the shipped files to this. Quartz's Information lines are startup and shutdown only.

- Retention periods: the `Retention` section (`LoginTokenDays`, `EmailDays`, `ReadNotificationDays`, `NotifiedEpisodeDays`, `DigestLedgerDays`, `ImportJobDays`, `PushSubscriptionDays`), in days; 0 or less disables that category. Keep `NotifiedEpisodeDays` well above the notification job's 3-day look-back, or users are notified twice.

## 12. Build, run and deploy

**One-time local setup**

```bash
dotnet user-secrets set "TheTvDb:ApiKey" "..." --project ./Recall.Web
dotnet user-secrets set "TheTvDb:Pin" "..." --project ./Recall.Web
dotnet user-secrets set "Omdb:ApiKey" "..." --project ./Recall.Web
dotnet user-secrets set "Login:AllowedEmails:0" "dev@email.com" --project ./Recall.Web

docker login dhi.io   # once: Docker Hub username and access token, for the hardened images
docker run --name my-redis -p 127.0.0.1:6380:6379 -d dhi.io/valkey:9.1 \
  --protected-mode no --save "" --appendonly no
docker run --name local_postgres -p 5432:5432 \
  -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=devpassword -e POSTGRES_DB=recall_db \
  -v local_pgdata_dhi:/var/lib/postgresql -d dhi.io/postgres:18.7-debian13
```

`local_postgres` keeps its name (`ui-review/review.sh` uses it). It moved to the hardened image on 2026-11-23 by dump and restore of each of its databases (other projects' databases live in it too); the old container is `local_postgres_old` on the volume `pgdata`, kept until the owner removes it. README's local setup has the move.

After the first start has created the schema, insert the dev user row into `app_user` (`11111111-1111-1111-1111-111111111111`, `dev-user`, `dev@example.com`). Without it, anything that writes user data fails on the foreign key.

**Run, build, migrate**

```bash
dotnet watch run --project Recall.Web --launch-profile Recall.Web   # https://localhost:7123
dotnet build Recall.sln --configuration Release
dotnet ef migrations add <Name> --project Recall.Web --startup-project Recall.Web
dotnet ef database update --project Recall.Web --startup-project Recall.Web
```

The cache container keeps the name `my-redis` (`ui-review/review.sh` uses it) and is published on host port 6380, which `appsettings.json` and `review.sh`'s default `REDIS_PORT` expect. It has no password locally, so its port is bound to loopback, and protected mode is off because the app reaches it through Docker's port forwarding, which Valkey does not count as loopback.

**CI/CD** (`.github/workflows/dotnet.yml`): on push and pull request to `main`, log in to `dhi.io` (secrets `DHI_USERNAME`, `DHI_TOKEN`; the PostgreSQL suite pulls `dhi.io/postgres` and `dhi.io/valkey`), restore, Release build, test `Recall.Tests` with coverage (summary only; coverage does not gate), then test `Recall.Tests.Postgres` in its own step (the runner's Docker starts the container; no coverage is collected there, so the summary reflects `Recall.Tests` only). On push, log in to `dhi.io` and GHCR, build `Dockerfile.prod`, push `ghcr.io/<user>/recall:latest` and `:<run number>`, then deploy over SSH (`appleboy/scp-action` and `appleboy/ssh-action`, the same host, user and key): upload the repository's `compose.prod.yml` and `deploy/dump_db.sh` to `~/recall-deploy` under temporary names; save the server's copies as `compose.prod.yml.prev` and `dump_db.sh.prev`, put the new ones in place (`dump_db.sh` keeps its path and name, mode 750: the daily backup cron job runs it from there); run `docker compose --env-file .env.prod -f compose.prod.yml config -q` and stop if it fails (both previous files are put back, so the folder never holds a mix, and nothing is pulled or started); then log in to GHCR, run `bash dump_db.sh`, `docker compose --env-file .env.prod -f compose.prod.yml up -d --pull always --wait --wait-timeout 180` (the deploy fails unless every container is running and healthy within three minutes, the app's own healthcheck included) and `docker image prune -f`. The script runs with `set -eu` (the SSH action does not stop at a failing command by itself), so a failing backup also stops the deploy. Every compose command there names the env file and the compose file. There is no lint or format step. `nightly-build.yml` logs in to `dhi.io` the same way and builds and tests the whole solution daily at 17:00 UTC, PostgreSQL tests included. `copilot-setup-steps.yml` starts `dhi.io/valkey:9.1` in a step (`--protected-mode no`, loopback port 6380, as locally), not as a service: a service container cannot be given a command, so it would keep protected mode on and refuse the job. Its Postgres is a service on `dhi.io/postgres:18.7-debian13`, with `credentials` of its own, since a service starts before the login step.

**The repository is the source of truth for every file the server runs except `.env.prod`**: `compose.prod.yml` and the server-side scripts in `deploy/` (today `dump_db.sh`). The deploy copies them to the server every time, so a change goes through the repository and a deploy, never an edit on the server (the next deploy would undo it). A new server-side file goes in `deploy/` and is added to the deploy's upload, its `.prev` copy and its restore on a failed check; a script there holds no secrets and reads what it needs from `.env.prod`. `.gitattributes` keeps `*.sh` and `compose.prod.yml` at LF line endings, and a script is committed executable (`git update-index --chmod=+x`). Every variable it interpolates is written `${NAME:?NAME must be set in .env.prod}`, so one missing from `.env.prod` fails the deploy's `config -q` instead of becoming empty; a new one must use that form. `.env.prod` is the only file maintained by hand on the server; a change that needs a new variable is deployed by adding it to the server's `.env.prod` first. `README.md` lists every variable `.env.prod` must contain ("Variables in .env.prod") and the rollback ("Rolling back the deployed files": `cp compose.prod.yml.prev compose.prod.yml`, then compose up with the env file; `cp -p dump_db.sh.prev dump_db.sh`).

**Hosting**: a single Docker host, single app instance (a permanent assumption).

**The app container** runs `Dockerfile.prod`'s image as UID 65532 (`nonroot`), with `/app` and its files owned by root, so the app can write only `/tmp`, its home folder and the two bind mounts: `./logs` → `/var/log/recallapp` and `./dataprotection-keys` → `/home/nonroot/.aspnet/DataProtection-Keys`. **Both folders must be owned by 65532 on the server**; the app refuses to start without a writable key folder (section 3). `WORKDIR` is `/app` and must stay so: Data Protection scopes its keys to the content root. The image's `HEALTHCHECK` runs `dotnet /app/Recall.Web.dll healthcheck` every 30 s (start period 90 s); compose does not repeat it. There is no shell in the container: debug with `docker debug recall_app` (Docker Desktop's tool, where available), or a `dhi.io/aspnetcore:10-dev` container joining the app's namespaces (`--pid container:recall_app --network container:recall_app --cap-add SYS_PTRACE`; the app's files are then under `/proc/1/root`), or `docker exec recall_app dotnet /app/Recall.Web.dll healthcheck`, which needs no shell. `README.md` has the commands. `compose.prod.yml` runs the app (logs and Data Protection keys on bind mounts), `dhi.io/postgres:18.7-debian13` on the volume `recall_pgdata_dhi` and `dhi.io/valkey:9.1` as the service `redis` (no snapshots or append-only file, `maxmemory 256mb` with `allkeys-lru` eviction: a pure cache that starts empty after a restart, which the app handles; section 7). Valkey requires a password, `VALKEY_PASSWORD` from `.env.prod` (compose refuses to start without it); the server must be logged in to `dhi.io` to pull it. `README.md` has "Switching production to Valkey", with its checks and rollback. Two ports are published, both bound to `127.0.0.1` only (since 2026-10-02, changed by the owner): the app's 8701 and Postgres' 5433 (for `psql` from the host). Neither is reachable from outside the server, whatever the firewall says (Docker's published ports bypass host firewalls such as ufw, which is why the binding matters); Valkey publishes nothing. Anything new that publishes a port should bind it to loopback the same way.

**The database container** (`postgres` service, container name from `POSTGRES_HOST`, `recall_postgres`) runs `dhi.io/postgres:18.7-debian13` with its data on `recall_pgdata_dhi`. That volume is declared `external` with that exact name: compose never creates or removes it (created by hand once, `docker volume create recall_pgdata_dhi`), so a deploy cannot quietly start on a new, empty one, and the app refuses an empty database besides (section 3; README, "A new server's first start"). The volume from before the switch, compose's `pgdata` (on the server `recall-deploy_pgdata`, holding the `postgres:18.1` data as of the switch), stays declared and unused as the rollback copy until the owner deletes it a few weeks after the switch (README, step 11 of "Switching production to DHI Postgres", then remove its entry from `compose.prod.yml`); nobody runs `down -v`, which would remove it. The app's `depends_on: postgres` has `restart: true`: compose restarts the app whenever it replaces the database container, so the startup checks always run against the database the app talks to (without it, a deploy that changed only the database left the app running, and `--wait` passed, since `/health/live` does not touch the database). The healthcheck is `pg_isready` as before; `dump_db.sh` works unchanged, since the image has `pg_dump`.

**Reverse proxy**: the app container sits behind nginx installed directly on the host (apt, systemd), which proxies to `http://127.0.0.1:8701` and is the only way in from the internet. nginx already sends `Host`, `X-Forwarded-For` and `X-Forwarded-Proto`; the app builds sign-in links from the scheme and host and keys its rate limiters on the client IP. The app's `TrustedProxies` default (loopback plus the private ranges) matches this setup, so it needs no server configuration: a request nginx sends to the loopback port reaches the container from the Docker bridge's gateway address, a private range.

**Backups**: `deploy/dump_db.sh`, shipped by the deploy to `~/recall-deploy/dump_db.sh`, run daily by a cron job on the server from that path and by every deploy before it starts anything. It reads `POSTGRES_HOST` (the container), `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD` from the `.env.prod` beside it (`ENV_FILE` overrides the path) and stops if one is missing; runs `pg_dump` through `docker exec` into the Postgres container; writes `/var/backups/recall/<db>_<UTC timestamp>.sql.gz` (umask 077) as `.partial`, renamed only after `gzip -t` passes; and only then deletes dumps older than 9 days. The cron entry itself is on the server, not in the repository. `README.md` has the restore commands; they read the user, database and password from `.env.prod` rather than spelling them out.

## 13. Conventions

- **Layering**: `Pages` → `Services` → `Infrastructure` → `Domain`/`Mappings`. In practice page models inject repositories directly for simple reads and writes; services exist where there is real logic.
- **Class style**: `sealed` classes with primary constructors; interface and implementation in sibling files; records for value shapes; `CancellationToken cancellationToken = default` as the last parameter on every async method; `Async` suffix throughout.
- **Nullable reference types** are on. `null` means "not found"; exceptions mean failure.
- **DI**: register through an `AddXxx` extension method. Options classes expose `const string SectionName`.
- **Mapping**: static `ToDomain()` / `ToEntity()` / `ToAggregate()` extension methods in `Mappings/`.
- **JSON**: always `RecallJsonOptions.Web`, so Redis and Postgres payloads stay compatible.
- **User feedback**: `this.SetSuccessToast/SetErrorToast/SetInfoToast/SetWarningToast(...)`; never write to `TempData` directly, read it only through `TempDataValueExtensions` (the cookie returns values as other types than were written; see "Toasts" in section 4), and never draw a toast outside the `_ToastMessages` partial. How long it stays follows from its kind and whether it has an action (`ToastDurations`, see "Toasts" in section 4); a new action in a toast is added to `ToastView.HasAction`.
- **Error handling in page handlers**: wrap in `try`, log, set an error toast, redirect or re-render. Jobs and fan-outs use `catch (Exception ex) when (ex is not OperationCanceledException)` so one bad item never aborts a batch.
- **Best-effort external calls**: reuse `ITheTvDbService.TryGetSeriesAggregateAsync` / `TryGetMovieAggregateAsync` (swallow and log) and `Task<T?>.AsOptionalAsync(...)` (swallows `TheTvDbApiException` only). A primary fetch failure should still propagate.
- **Episode ordering**: `EpisodeOrderingExtensions` has the two orders and nothing else should sort episodes: `OrderBySeasonAndEpisode` (TheTVDB's listing order, specials first; notifications, raw episode loads) and `OrderByWatchOrder` (specials last; everything about watching, through `WatchProgressCalculator.Order`).
- **Recording a watch**: call `IWatchProgressService`; it validates the series/episode pair and the air date, and records the right `WatchSource`. Page handlers map the returned outcome to a toast and pass the result's `CaughtUp` to the toast helper (`SetWatchedToast` or `SetSuccessToastWithWatchedUndo`); never set a second toast for it. The service also adds the series to the library, and resumes it if the user had stopped watching it; a page never does either itself after a mark, it only words `AddedToLibrary` or `ResumedWatching` into the toast (`MarkLibraryEffect.Clause`).
- **Stopped series**: ask `SeriesLibraryStateRule` (`IsStopped`, `Followed`, `Of(..., stopped)`, `CanStop`), never `StoppedUtc` directly; stop and resume through `IWatchProgressService`. See "Stopped watching" in section 5.
- **Anything laid out over time** (a chart, a "this month" figure, a streak if one is ever built) counts only watches whose source `IsDated`; totals count every row. See "Watch source" in section 5.
- **Charts** are server-rendered lists with their figures in text; see "Stats" under "Design system". No chart library, no script.
- **TheTVDB cost of a series**: fetching or refreshing a series is a fixed few requests (section 7). Never add a request per episode to that path; read episode fields from the extended record or the translated episode list, and keep single-episode requests lazy, on the page that needs them.
- **Movie watchlist and watched state**: call `IMovieTrackingService`; it keeps "on the watchlist" and "watched" mutually exclusive, and takes the `WatchSource` of a new watch.
- **Parallelism**: only fan out over code that uses `IDbContextFactory`. Never run two operations on the scoped `AppDbContext` at once.
- **Logging**: structured message templates with `ILogger<T>`; no string interpolation in log calls. Levels are set in `Serilog:MinimumLevel` only; there is no `Logging` section, and one would be ignored. Per-request, per-query and per-call framework logging stays at Warning (see "Logging" in section 10); a job or service that wants a figure in the log writes one summary line of its own at Information.
- **Time**: inject `TimeProvider` (registered as `TimeProvider.System`) wherever the current date decides behavior, and get the date with `AirDate.Today(timeProvider)` — the UTC date, the same on a developer machine and in production — or the moment with `AirDate.Now(timeProvider)`. Whether an episode is out is its release moment (`EpisodeRelease.MomentUtc`, `IsReleasedBy(now)`); whether it may be marked watched is `AirDate.MayBeMarked(aired, now)`. Do not compare an air date with today's date to decide either. Do not call `DateTime.Today`, `DateTime.Now` or a static clock. Views read `Model.Today`. Persistence timestamps still use `DateTime.UtcNow` directly, except `EpisodeWatchRepository`'s `WatchedUtc`, which comes from its optional `TimeProvider` so tests can put two marks in one instant.
- **Retention**: a new table that only ever grows needs a delete in `IDataRetentionRepository`, a period in `RetentionOptions`, and a line in `PruneOldDataTimer`. Each category is its own `ExecuteDeleteAsync` in its own try/catch.
- **Audit columns**: an entity with `CreatedUtc` and `UpdatedUtc` implements `IHasAuditTimestamps`; never set either by hand.
- **Handlers on public pages** start with `currentUserService.TryGetUserId(out var userId)`; do not re-derive the check from `IsAuthenticated`.
- **Comments**: the codebase explains *why* in comments and XML docs on non-obvious code; keep that density.
- **SEO**: pages are `noindex` unless they set `ViewData["Robots"]`.
- **Design system**: tokens, type scale, icon constants, the page frame, `_EmptyState` and `DisplayDate` are described under "Design system" in section 4. In short: no literal colours, font sizes or radii outside `tokens.css`; no `!important`; icons through `Icons.*`; dates through `DisplayDate`; one `h1` per page; mono for data only.
- **Culture**: the process culture is pinned to `en-US` (`Infrastructure/Hosting/AppCulture.cs`). Do not set `LANG`/`LC_ALL` in images or add request localization; machine-readable output (sitemap dates, JSON-LD, anything parsed back) should still pass `CultureInfo.InvariantCulture` explicitly.
- **Public pages and quota**: a page reachable without sign-in must not call OMDb, and if it can trigger a TheTVDB fetch it needs the `public-details` rate-limit policy. `PublicDetailsRateLimitTests` checks the three current pages carry it.

## Observations

Ranked by impact. Items marked fixed are kept for the record, with whatever remains of them.

1. **Anonymous pages spending upstream quota: fixed for OMDb, bounded for TheTVDB.** Anonymous requests never call OMDb, the Details pages are rate-limited per anonymous IP, and the sitemap is capped. What remains by design: an anonymous visitor can still make the app fetch an uncached title from TheTVDB (up to 60 pages a minute per IP, three requests per uncached series), and each such fetch adds rows to the cache tables and, later, URLs to the sitemap. A crawler spread across many IPs is not bounded by the per-IP limit.
2. **Forwarded headers trusted from any source: fixed in the app.** `X-Forwarded-*` is applied only when the request comes from loopback or a private range, which is how nginx on the host reaches the container. A caller arriving from a public address cannot forge its client IP, and since the app's port is bound to `127.0.0.1` no such caller can reach the container directly at all.
3. **Sessions that could not be revoked: fixed, within 5 minutes.** Deleting or demoting a user takes effect at the next revalidation. A user can delete their own account (section 5). There is still no "sign out everywhere" for a user who keeps their account, and no admin UI to do either; both remain manual database edits.
4. **No HTTP resilience: fixed.** Both metadata clients retry transient failures; see section 7. Not added: a circuit breaker, so a long TheTVDB outage still costs every request its retries.
5. **Cached aggregates never refreshing: fixed.** Rows without `KeepUpdated = true` are now refreshed every 30 days. Remaining: `cached_series_extended` still has no refresh path, but nothing reads it any more (`ITheTvDbService.GetSeriesByIdExtendedAsync` has no caller outside tests), so the table and method are candidates for removal. The refresh cap (10 series and 10 movies an hour) bounds how fast a large, crawler-filled cache cycles.
6. **Two sources for a series' episode list: fixed.** Display, progress, "mark watched through" and the prior-unwatched prompt all read the aggregate.
7. **Write handlers trusting client-supplied id pairs: fixed for watches, likes and ratings on episodes.** They go through `IWatchProgressService` or refuse when the parent series can't be resolved. Still unvalidated: series and movie like/rating handlers accept any positive id without checking it exists on TheTVDB.
8. **Single-instance assumptions.** Login abuse limits, the OMDb daily budget, the TheTVDB token and the Quartz schedule are all in process memory, and migrations run at startup. Every deploy resets the OMDb budget and login counters. A second instance would double every job.
9. **Test gaps: mostly fixed.** Page models, all jobs, `LoginAbuseGuard`, `TurnstileVerifier`, `OmdbApiClient` and a small pipeline suite are tested, and `Recall.Tests.Postgres` runs the migrations, the `UniqueViolation` catch blocks, the `xmin` token, `jsonb` and the provider-specific queries against real PostgreSQL (see section 11 for what remains). Writing those tests found that `EpisodeWatchRepository.MarkWatchedAsync`, `LikeRepository.ToggleAsync` and `MovieWatchRepository.ToggleAsync` left the row that lost the race pending in the context; they now detach it. Still open: CI coverage is informational only and does not include the PostgreSQL tests.
10. **Dead or unused code and dependencies: fixed.** The four unused packages, the controller and session registrations, the unused Redis multiplexer, `AppDbContextFactory`, `UserItem`/`UserMappings`, `site.js`, the empty import map and the stale csproj items are gone. Left alone: `Microsoft.AspNetCore.Mvc.Testing` in the test project (unused, see 9). The IDE-generated `Recall.Web/Dockerfile` and `compose.yaml` were deleted on 2026-11-22 (open questions).
11. **Convention drift: mostly fixed.** "Already in your library" is a return value, the admin counts come from `IAppUserRepository`, and movies and episodes have their own OMDb types. Remaining: `IAppUserRepository` still returns entities, and `EpisodeOmdbSnapshotStore` uses the scoped context while its two siblings use the factory.
12. **State-changing GETs: fixed.** Logout and notification-open are POST-only. Convention: anything that changes state is a POST handler behind the antiforgery token.
13. **Unbounded tables: fixed.** `PruneOldDataTimer` deletes settled login tokens, finished emails, read notifications, the notified-episode ledger and completed imports on the periods in `Retention`. By design it keeps unread notifications and anything still in progress, so an account that never reads its notifications still accumulates them.
14. **Duplication: partly fixed.** `ApplyAuditTimestamps` is one loop over `IHasAuditTimestamps`, and the Details POST handlers share `TryGetUserId`. Deliberately left: the three OMDb snapshot stores and the two OMDb jobs are still near copies.
15. **Local time for air dates: fixed.** Every air-date check, and the Dashboard header, uses the UTC date from an injected `TimeProvider`. There is still no notion of the user's time zone.
16. **Deployment details.** The Swedish locale is gone: `Dockerfile.prod` no longer generates or sets `sv_SE.UTF-8`, and the app pins its own culture (`AppCulture.PinToEnglish`, `en-US`) at startup, so dates and numbers render in English whatever the host is set to. This was confirmed, not inferred: on a Swedish-locale machine the Dashboard header read "torsdag, oktober 1" before and "Thursday, October 1" after. Fixed on 2026-11-22 with the move to hardened images: the log directory is no longer `chmod 777` (it and the key folder are owned by 65532) and the unused fonts are gone. The Copilot setup workflow's `postgres:16-alpine` is gone too: everything runs `dhi.io/postgres:18.7-debian13` since 2026-11-23.
17. **Stale documentation and comments: fixed.** `AGENTS.md` is a pointer to this file, the README backup commands no longer `cd` into a Receptus folder, and the comments about where jobs are scheduled, where cookie auth is wired, and which pages are public are corrected. The README's backup and restore commands now match production (see section 12).
18. **Debug builds log the raw login token** (`PasswordlessAuthService`, inside `#if DEBUG`). Deliberate for local sign-in, but a Debug build must never be deployed.
19. **Push on an iPhone needed a sign-in inside the Home Screen app: fixed.** The emailed link opens in Safari, and a Home Screen app has its own cookies; every sign-in email now also has a one-time code to type into the app (section 8). Not yet tried on a device.

## Quick facts

- **Stack**: ASP.NET Core 10 Razor Pages, C# 14, one web project plus two test projects. Tracks series (library + per-episode watches) and movies (watchlist + watched).
- **Data**: PostgreSQL 18.7 (Docker Hardened Image) through EF Core 10 (Npgsql); Valkey 9.1 (Redis protocol, Docker Hardened Image) as a read-through cache; metadata stored as JSON snapshots, not relational tables.
- **External APIs**: TheTVDB v4 (primary metadata), OMDb (IMDb ratings), Cloudflare Turnstile, SMTP.
- **Auth**: passwordless magic link → 30-day cookie; roles `User`/`Admin`; Debug builds auto-sign-in as a fixed admin.
- **Jobs**: nine Quartz.NET jobs, in-memory schedule, single instance.
- **Push**: Web Push (VAPID) to installed or browser subscriptions, one summary push per device per run, quiet hours 22:00–08:00 per device; off unless `Push:Enabled`.
- **Front end**: Bootstrap 5.3.3 themed through CSS variables, Phosphor Icons, self-hosted fonts, jQuery for validation; all vendored through `libman.json`, no build step.
- **Run**: `dotnet watch run --project Recall.Web --launch-profile Recall.Web` (needs local Redis and Postgres) → https://localhost:7123
- **Build**: `dotnet build Recall.sln --configuration Release`
- **Test**: `dotnet test Recall.sln` (1,744 tests, NUnit; SQLite in-memory for persistence, plus a Testcontainers PostgreSQL suite that needs Docker and is skipped without it)
- **Deploy**: push to `main` → GitHub Actions → GHCR image → `docker compose -f compose.prod.yml up -d` over SSH.
